# 自包含评审清单

评审时按本清单逐项核对。命中「高危信号」即记录为一条发现。

## A. 知识自包含（核心维度）

- [ ] 规范 / 经验 / 领域知识是否全部在技能文件内？
  - 检查：是否存在 `references/` 且该目录下的文件内容完整（调色板、命令、字段、公式、示例等），而非只有占位或「详见外部文档」。
- [ ] 是否调用宿主专有「知识接口」命令去获取规范？
  - 高危信号：`read_me`、`modules: ["..."]`、`show_widget`（用于拉取规范 / 设计系统）、Visualizer 等，且规范本身**不在**技能内。
  - 命中即「知识未内置」。
- [ ] 是否有「若 X 不可用则回退到 references」之类的首选外部、兜底内置措辞？
  - 命中说明内置只是兜底，知识仍依赖外部 → 不独立。
- [ ] 示例 / 少样本是否内置？
  - 检查 `references/*.svg | *.md | *.json` 是否包含可对齐的示例，而非「请参考外部资源」。

## B. 宿主绑定（可移植性维度）

- [ ] 是否写死某个 AI 软件的私有路径？
  - 高危信号：`C:\Users\...\ .workbuddy\...`、`~/.workbuddy/`、或其他软件专属目录出现在命令或说明里且不可替换。
  - 命中即「绑定宿主」→ 不独立（除非明确标注为「用户需替换为自身路径」的占位）。
- [ ] 是否依赖仅某客户端才有的专有命令？
  - 如仅供某个 AI 客户端使用的 `show_widget`（渲染）、`read_me`（加载）。若技能离开该客户端就无法运行，则不可移植。

## C. 工具依赖（豁免项，不算不独立）

- [ ] 是否声明工具由用户自备？
  - Node.js、Python、浏览器、CLI 工具等属于用户环境，技能应说明「需本机具备 X」，而非假设某个软件的私有安装存在。
- [ ] 是否用通用命令而非私有路径调用工具？
  - 正确：`node script.mjs`（依赖 PATH 中的 node）。
  - 错误：`C:\Users\...\ .workbuddy\binaries\node\...\node.exe script.mjs`（写死私有路径）。
- [ ] 找不到工具时是否提示用户安装并结束，而非假设已存在？
  - 良好实践：开头加环境检查步骤，缺失即提示安装并终止。

## 严重度

- **阻断**：知识靠外部拉取；写死宿主私有路径。
- **建议**：工具声明不清、缺少环境检查、示例不全但不影响运行。
