# 02 · 感知规范

> **什么时候读**：改识别算法、改 state 输出、球认错/认漏、识别太慢拖垮帧率。
> **本文件定义感知层的输入输出契约**——契约变了，下游 `03` 与 `04` 必须同步改。

---

## 一、契约（先定契约，再写实现）

```
截图(Image) ──► 感知(perceive) ──► state(JSON 对象) ──► 快循环 / JEV
```

- **输入**：`images.captureScreen()` 的返回值。
- **输出**：一个**纯 JS 对象**（可直接 `JSON.stringify` 喂给 JEV 的结构）。
- **硬约束**：感知层**只做几何与颜色**，不做任何"要不要吃"的决策——那是决策层的事。感知层不许调用网络。
- **「自己」可能是一组球**：自己最多可分成 **16 个球**（用户确认，2026-09-23）。所以 `self` 不是一个圆，而是**一组同色碎片**：`self.n` 记碎片数，`self.x/y` 取整组**质心**，`self.r` 取按总面积折算的**等效半径**（不是最大碎片半径），逐片几何放 `self.pieces`。

## 二、state schema（唯一权威定义；JEV 的输入从这里裁）

```javascript
{
  "ts": 1700000000000,          // 毫秒时间戳
  "frame": 1234,                // 帧序号（自增）
  "self": {
    "x": 540, "y": 960,         // 屏幕坐标（多碎片时 = 整组质心）
    "r": 20,                    // 半径(px)（多碎片时 = 按总面积折算的等效半径）
    "n": 1,                     // 自己的碎片数，1~16；1 表示未分身（也含刚分身又合体的状态）
    "pieces": [                 // 长度必须 == n；n==1 时只留一片
      { "dx": 0, "dy": 0, "r": 20 }   // 相对质心的位移(px) + 该片半径
    ]
  },
  "balls": [                    // 按距离升序，最多 MAX_BALLS 个；**只放其他球，不含自己的碎片**
    {
      "dx": 120, "dy": -80,     // 相对自己球的位移(px)
      "dist": 144,              // 距离(px)
      "r": 12,                  // 半径(px) = max(r_area, r_ref, r_occl)
      "size_ratio": 0.6,        // r / self.r —— 口径＝【直径比】(≡半径比)，见 §四；须用同一帧尺寸
      "r_area": 12,             // 面积/bbox 兜底半径(px)     ← 2026-09-25 加（半径口径溯源）
      "r_ref": 0,               // Hough 精化半径(px)，0=未精化 ← 2026-09-25 加
      "skin": 1,                // 皮肤球标记（半径是**下界**，见 §3.1b）
      "refined": 0,             // 本球是否走了 Hough 精化
      "r_occl": 0,              // 贴身遮挡下界(px)，0=未触发     ← 2026-09-25 加（见 §3.7）
      "unreliable": 0,          // 1 = 轮廓不完整且压在自己身上 ⇒ 决策层**不许当它可吃** ← 2026-09-25 加（§3.7）
      "edible": true,           // 是否可吃（依 §四 规则）
      "threat": false,          // 是否构成威胁
      "vx": 1.2, "vy": -0.4,    // 估算速度(px/帧)，未知则 null
      "kind": "unknown"         // dumb_bot / smart_bot / human / unknown
    }
  ],
  "bounds": {                   // 相对自己球到四边的距离(px)，用于贴边判断
    "left": 400, "right": 600, "top": 300, "bottom": 700
  },
  "recent": {                   // 近期执行结果，供 JEV 判断动作是否奏效
    "action": "chase",          // 上一次慢循环选定的策略
    "since_ms": 900,
    "ate_delta": 2              // 这期间吃到的球数（可为负=被吃，但被吃就结束了）
  },
  "stats": {
    "frame_ms": 78,             // 本帧感知耗时
    "balls_found": 17,
    "clusters": 19,             // 噪声地板后的簇数（§3.2）
    "frag_merged": 3,           // 碎片聚合实际合并次数（§3.1，持续偏高=过分割严重）
    "self_n": 1,                // 本帧 self 碎片数（== self.n）
    "noise_dropped": 4,         // 被噪声地板丢掉的簇数（§3.2）  ← 2026-09-25 加
    "balls_precap": 19,         // 截断到 MAX_BALLS **之前**的球数  ← 2026-09-25 加
    "max_balls": 12,            // 当时生效的截断上限              ← 2026-09-25 加
    "occl_boost": 1,            // 本帧有多少球被贴身遮挡下界抬高了半径 ← 2026-09-25 加（§3.7）
    "occl_unreliable": 2        // 本帧有多少球被判「尺寸不可信」       ← 2026-09-25 加（§3.7）
  }
}
```

**字段规则**：

- 估算不出来的字段写 `null`，**不许编造**（例如速度在只有单帧时无法估算）。
- `self.n` 上限 **16**（游戏规则）；`self.pieces` 长度必须恒等于 `self.n`，**不许长度对不上**。
- **自己的碎片不进 `balls`**：`balls` 只描述其他球。判自我时不能只看颜色——其他玩家的球也可能是紫色（见 `01` §四），须叠加屏幕中心区域与描边约束。
- `balls` 必须**截断到 `MAX_BALLS`**（默认 12），并按「威胁优先、其次距离」排序——因为慢循环的 state 里放太多球会稀释 JEV 的注意力，也涨 token。
- 无球时 `balls: []`，不要返回 `null`。
- **半径口径溯源（2026-09-25 加）**：`r = max(r_area, r_ref, r_occl)`（精化只增不减、遮挡下界只抬高）。
  决策/排查时**必须在原值上比**：`size_ratio` 用 `r` 算，所以"换个阈值会不会可吃"要靠
  `r_area`/`r_ref` 离线复算。这是重估 `EAT/THREAT` 阈值的数据基础。
  ⚠️ **`r_occl` 目前落不了盘**（2026-09-25 真机实测证伪）：`state.balls[]` 里有它，但
  `aim.js#snap()` 输出的球对象**不带 `r_occl`**，`03` §3.6 的 aim 日志因此拿不到它
  ——要离线复算腿①必须先给 `snap()` 补这个字段。
- **`unreliable` 是"量不准"标记，不是"危险"标记（2026-09-25 加，§3.7）**：它只说
  「这颗球的尺寸我测不准，而且它正压在我身上」⇒ 决策层不许把它当追吃目标。
  `edible`/`threat` 仍按 `size_ratio` 如实算，**不要**用 `unreliable` 去改 `edible`
  （那会让日志自相矛盾、无法复盘）。

## 三、处理流水线（已定案并实现：扫描线内联分类，2026-09-23 真机实测择优）

> 原「路线 A 扫描线游程 / B 反射 OpenCV / C 模板匹配」三选一已定案：**采用 A 并已实现**。
> B 依赖 6.8.0 外部 OpenCV 插件（未装即抛异常，未实测，不采用）；C 只在 A 彻底不可用时才考虑。
> 被实测推翻的具体路径（cvtColor+inRange / readPixels / 异步帧）见 §7.2，不再重复。

```
captureScreen(全屏)
  → images.resize(400x180, "AREA")            // DOWNSCALE=8
  → getBitmap().getPixels()                   // 一次性取回 ARGB 数组
  → 扫描线采样点内联 RGB→HSV 判定 → 游程       // 热路径，禁调函数/禁建对象；双车道 OR（§3.6）
  → clusterRuns   贪心聚类（行相近+x重叠 → 簇，带 bbox）
  → mergeFragments 碎片聚合（§3.1）
  → noiseFloor    噪声地板（§3.2）
  → dropUiAchroma UI 区内的无彩色簇丢弃（§3.6）
  → selectSelf    self 组识别（§3.3）
  → state（§二 schema；stats.ui_dropped = 本帧被 UI 判据丢掉的簇数）
```

### 3.1 碎片聚合与贪心聚类判据（2026-09-24 三刀修复，均有真机实锤）

**背景**：01.jpg 对照实验（探针跑生产管线 vs PC 全像素复算）实锤两类链式误并，
两者叠加把 self 撑成 155-run 巨簇（r 虚胖 24%、身边可吃球全部消失）：

1. **贪心聚类"引力井"**：归簇 x 判据原为 `|run.cx - 簇.cx| ≤ max(len, lenMax)`——中心距离而非
   区间重叠。宽球（self lenMax≈130ds）周围形成引力井，x 完全分离的邻球也被链式吸入。**已修**：
   改为 `min(r.x2,b.x2)-max(r.x1,b.x1) ≥ 0`（x 区间真重叠）。
2. **异色串珠**：空间连通挡不住"桥接彩豆把异色球串成竖链"（长颈鹿+我超凶的×2 被橙红桥豆
   串成一簇）。**已修**：归簇加**锚 hue 校验**——run 中心像素 hue 与簇锚 hue（首个可信 run 的
   hue）环距 > `FRAG_MERGE_HUE_TOL` 拒归；S/V<30（标签白点/暗点）hue 不可信放行；px 缺省
   （PC 冒烟）跳过。
3. **碎片合并允许负 gap**：`b.yTop - a.yBot ≤ GAP` 无下界，bbox 重叠/相贴的真球被当标签切缝
   拼进 self。**已修**：gap 必须 ∈ [0, GAP]（老板拍板"真有缝才拼"），合并前再加簇质心色相校验。

**修复效果（01.jpg 第三轮探针）**：self (1694,884) r=368 → **(1594,668) r=294**（PC 真值
(1592,716) r≈297）；身边可吃玩家球 0 颗 → 4+ 颗独立成球（绿刺 hue117 / 长颈鹿 / 我超凶的×2）；
threat=0 与真值一致。冒烟 12/12 PASS。

| 常量 | 值（config.js） | 状态 |
|---|---|---|
| `FRAG_MERGE_GAP` | `8`（降采样px） | **已修**：gap ∈ [0,8] 拼标签切缝；**负 gap 同色开口子**（见下） |
| `FRAG_MERGE_OVERLAP` | `0.5` | 沿用（负 gap 开口子同用此阈值：x 重叠 ≥ 0.5×min(两簇宽)） |
| `FRAG_MERGE_HUE_TOL` | `12`（度，色相环距离） | **已定**（2026-09-24 老板拍板"拼前比颜色"；与 SELF_HUE_TOL 同值但独立常量，可分开调） |
| `SKIN_FILL_MAX` | `0.5`（bbox 填充率） | **已定**（2026-09-24 神烦狗实锤后新增，见 §3.1b 皮肤球兜底） |

**负 gap 同色开口子（2026-09-24 二次拍板）**：负 gap（bbox 重叠）默认仍是两颗紧挨真球拒并，
但多色皮肤球自身碎片（02.jpg 神烦狗：红环被白狗脸切 4 片，bbox 重叠、同色、x 重叠 90%）例外。
开口子三条件缺一不可：① 有像素数组 ② x 重叠 ≥ OV×minW ③ **hueSame 严格同色**
（色相环距离 ≤ HUE_TOL；色相不可信不放行——与正 gap 的 hueClash"不可信放行"方向相反，
因为负 gap 是高危区）。回归：01.jpg self r=296 无回归、绿刺球仍独立；02.jpg 狗主簇 r=101→180。

**已知残留**：皮肤球自身色相散布（红环 0/356 + 狗脸 22 + 橙 36）> HUE_TOL=12，
跨色相碎片拼不全（02.jpg：hue356 碎片因合并簇质心落在狗脸 hue22，色相差 26° 被拦）。
靠 §3.1b 皮肤球兜底 + 决策层护栏弥补，根治待描边找圆（findCircles，PC 离线验证先行）。

### 3.1b 皮肤球半径兜底（2026-09-24 02.jpg 神烦狗实锤新增）

多色皮肤球（名字球/活动球的花色皮肤：白脸、图案、高光）大面积过不了 HSV_BALL 色域门，
彩色像素只剩外圈 → **面积法半径是下界**（神烦狗：面积 r=114 vs 真值 243，低估 53%）。

- 判定（`isSkinBall`）：bbox 填充率 = 彩色像素×行步长/(bboxW×bboxH) < `SKIN_FILL_MAX`(0.5)
  且 bbox 近圆形（宽高比 0.7~1.43，排除彩豆串）。实心圆填充率 ≈ π/4 ≈ 0.79，绿刺球实测 0.86 不误伤。
- 兜底（`ballRadiusOf`）：皮肤球半径 = max(面积半径, bbox 半宽)。红环贴球缘，bbox 接近真边界；
  神烦狗实测 r 101→180（真值 243，仍低估 ~26%）。**球对象新增 `skin: 1` 标记**，
  供决策层护栏用：皮肤球 size_ratio 是下界，测得 0.69 真值可能是 0.93+。
- **待办（决策层）**：skin=1 且 ratio ∈ [~0.65, THREAT] 的球按近身球处理（不当可吃）；
  根治 = 描边找圆。

已知边界：碎片聚合只处理**纵向切割**（横向切割罕见，未处理）；贪心聚类逐 run 算 hue 仅数百次/帧，
不碰逐像素热路径。

### 3.2 噪声地板（放在碎片聚合**之后**）

`area ≥ SCAN_COL_STEP×3 且 rows ≥ 2` 才保留。顺序很关键：被标签切下的单行碎片单独过不了地板，并回母球后才有资格——这是「认漏」修复的一部分。**已知取舍**：直径只有 1~2 个扫描行的最小彩豆永远只有单行，会被丢（TBD-9 标定孢子/彩豆尺寸时一并复核）。

### 3.3 self 组识别（2026-09-24 阶段2 重写，替换旧的"取最大最近单球"）

自己 = **一组同色碎片**（02 §一）。三重判据：

1. **颜色**：簇内取 5 个采样点（中心 + 四角内缩点）判 `HSV_SELF`，任一命中即算——只采质心会被名字标签（白色低饱和）骗过；
2. **中心先验**：簇中心在 `SELF_SEARCH_RADIUS` 内（镜头恒追自己质心）；
3. **色相一致性**：候选 ≥2 时取中位色相为锚，偏离超 `SELF_HUE_TOL`（`12` 度，未标定）剔除——防同色系敌球混入。

上限 `SELF_MAX_PIECES=16`，超出按面积取最大的 16 个。输出：`self.x/y`=整组质心、`self.r`=**按总面积折算的等效半径**、`self.n`+`self.pieces`（相对质心位移+该片半径）。自己的碎片标记 `isSelf`，不进 `balls`。

> **已知局限（待更硬的区分特征）**：色相与自球相近（±12°）的敌球贴到中心区仍可能混入 self 组；02 §六有记录。后续可引入描边色约束。

### 3.4 半径口径修正（2026-09-24 冒烟测试发现的旧版隐性 bug）

`radiusOf(area) = √(area × SCAN_ROW_STEP / π)`——每个采样游程代表 `rowStep` 行的内容，**旧版没乘 rowStep**，绝对半径系统性低估 ≈√3≈1.73 倍。影响：computeAim 的 gap、bounds 的「球边缘→边界」距离、威胁距离。**不影响 size_ratio**（ball.r/self.r 两边同乘约掉）。真机 v0.6.0 起 `self_r` 日志值会比 v0.5.0 系统性变大 ~1.7 倍，属预期，不是回归。

## 四、可吃 / 威胁判定（游戏常数，需标定）

```
edible  = size_ratio < EAT_RATIO_THRESHOLD      // 明显小于自己 → 可吃
threat  = size_ratio > THREAT_RATIO_THRESHOLD   // 明显大于自己 → 威胁
near_tie = 两者之间                              // 同级别，规则由决策层定
```

| 常量 | 值 | 怎么定 |
|---|---|---|
| `EAT_RATIO_THRESHOLD` | `0`（未标定） | 真机试验：找两个大小接近的球，逐档缩小差距，看多大差距还能吃掉 |
| `THREAT_RATIO_THRESHOLD` | `0`（未标定） | 同上，取倒数附近再留余量 |

> 球球大作战通常需要**明显大于**对方才能吃掉（不是大于一点点）。这个倍数必须实测定，**不许照抄其它游戏的经验值**。

> **✅ 口径已定（用户 2026-09-23）：按【直径】算**——"大 5%~10%"里的百分比指**直径差**。理由：**所有玩家球都近似圆形**。
> - ⇒ **直径比 ≡ 半径比**，所以 schema 里的 `size_ratio = ball.r / self.r` **本身就是口径所需的值，不需要任何换算**（体积口径已排除）。
> - ⇒ 折算阈值：`EAT_RATIO_THRESHOLD ≤ 1/(1+Δ)`，Δ∈[0.05, 0.10] ⇒ **估计区间 `0.909 ~ 0.952`**（中值 ≈ `0.93`）。
> - ⚠️ **估计值≠实测值**：`config.js` 里该常量**保持 `0`**，`assertCalibrated()` 继续拦启动，直到真机实测命中（`00` §六 `TBD-11`）。
> - ⚠️ **量直径的实现注记**：玩家**皮肤**带耳朵/小脚会拉长轮廓，**不要直接取"最长边"**；用**最小外接圆直径**或**面积等效圆直径**（对近似圆等价、且抗外延部件污染）。详见 `00` §三 M07 的实现注记。

## 六、常见误判与对策（遇到新的就往这里加）

| 现象 | 可能原因 | 对策 |
|---|---|---|
| 认不出自己球 | 描边色/名字标签干扰色域 | 用"球心在屏幕中心附近"作先验，取候选里最接近中心且最大的那个 |
| 球被切成两半 | 球上有名字标签或高光 | 形态学闭运算（`images` 无此函数 → 用两次 `blur` 近似，或放宽色域后按距离聚类） |
| 一直认到同一个"球" | 背景里有同色 UI 元素 | 把 UI 区域加进屏蔽矩形列表，扫描时跳过 |
| 球数忽多忽少 | 边界被裁切 | 允许圆心在屏幕外、只保留部分可见的球 |

## 七、AutoJS `images` API 实测要点（2026-09-23）

> **官方全文已离线存档**：`autojs-mobile-automation-yashu/references/autojs6_images_doc.md`（**AutoJs6 6.8.0**，含 `readPixels` / `countPointsByColor` / `findCircles` / `buildRegion` / `getMeanColor` / `matchFeatures` 等新增项）。**先 Grep 函数名再局部读，严禁通读**（6.2 万字符）。
> 本节只记**本项目实测出的、官方文档没写或与正文相冲突**的部分——改感知层前必读本节。

### 7.1 已采用的路径与实测耗时

| 环节 | 采用 | 实测 |
|---|---|---|
| 截图 | `captureScreen()`（**同步**） | **72ms** 稳定（5/5 次 70–72ms） |
| 降采样 | `images.resize(img, [W, H], "AREA")` | 3200×1440 → 800×360 约 **2–13ms** |
| 取像素 | `img.getBitmap().getPixels(arr, 0, W, 0, 0, W, H)` | 整幅约 **1–3ms** |
| 颜色判定 | **JS 内联 HSV 判定**（只算扫描线采样点） | 1.2 万次迭代 ≈ **34ms** |
| **完整一帧** | 上列串联 | **113–220ms**（目标 ≤150ms） |

> **`images.resize` 只有数组重载**：`resize(img, [w, h], "AREA")` 有效，`resize(img, w, h)` **不是有效重载**。

### 7.2 被实测推翻、不要再走的三条路

1. **`cvtColor` + `inRange` 做 HSV 掩膜 —— 放弃。**
   - `inRange` 的参数类型是 `ColorInt | ColorHex | ColorName`，对 `cvtColor` 后 HSV 图的**通道序无任何文档保证**；
   - 决定性反证：某探针点理论 OpenCV HSV 应为 `H=155`，而 `images.pixel` 在该 HSV 图上读回 `H=145` ⇒ **在 cvtColor 产生的 Mat 上读值不可信**；
   - ⇒ 掩膜内容无法验证 = 把感知建立在猜测上。改为**只对扫描线采样点在 JS 里内联算 HSV**；并把同一张降采样图拉回 PC 用 numpy 复算 → 彩色像素 8343、占比 **11.6%**、游程 **258** 与设备端**逐位一致**（可自证）。
2. **`images.readPixels(image)` —— 对本工程不可用。** 直接抛 `ImageWrapper ... is invalid`。继续用 `getBitmap().getPixels()`。
3. **异步帧模式 —— 更慢，放弃。** `requestScreenCapture({isAsync:true})` + `images.on("screen_capture_available")` 实测仅 **8.4 fps**（72 帧/8.5s），慢于同步路径的 ~11 fps。

### 7.3 两个必须记住的坑

- **`captureScreen()` 可能返回上一帧的副本**（官方文档明说：截图暂时失败且已有可用上一帧时返回上一帧）。⇒ **任何"连续两帧完全一致 ⇒ 球静止 / 摇杆没生效"的推断都不可靠**——曾据此误判"推杆后球没动"。**必须加重复帧守卫**（比对帧指纹，重复即丢弃重截），成本≈0。
- **`inRange` 输出的"0"不是 `0`，而是 `0xFF000000`（不透明黑）**。判定命中要按白色 `-1`，不能写 `!== 0`——曾因此把 72000 当成命中数。

### 7.4 资源管理（踩过 OOM）

- `captureScreen()` 返回的图**由截图模块托管，不要手动 `recycle()`**（曾误回收）。
- 其余 `ImageWrapper` **必须** `recycle()`。**反例**：探针把 5 张 3200×1440 整屏图留在数组里不回收（每张约 18MB × 5）→ **AutoJS 引擎 OOM 被杀**，手机弹"调用失败"气泡。
- **性能归因（重要经验）**：单次 `images.pixel()` 实测仅 **5µs**（4.8 万次共 240ms）⇒ **JNI 不是瓶颈**。旧实现 1825–2612ms/帧的真凶是 **Rhino 解释器**：逐像素调用 5 个函数 + `argbToRgb`/`rgbToHsv` 每像素各 `new` 一个对象 ≈ **9.6 万次对象分配/帧**。
  ⇒ **AutoJS 里的性能瓶颈几乎总是「JS 侧迭代次数与对象分配」，不是原生 API 调用次数。**

### 7.5 未采用但值得试（6.8.0 新增，尚未实测）

| 接口 | 潜在用途 |
|---|---|
| `countPointsByColor(img, color, {region, threshold})` | 原生掩膜计数、不生成点数组 → 判"某区域是否大部分为某色"（按钮是否亮起、自球是否被遮挡） |
| `findCircles(img, {region, minRadius, maxRadius, param1, param2})` | Hough 圆检测**直接给圆心 + 半径** → 拿球半径的捷径（当前靠扫描线游程估半径） |
| `buildRegion(img, region)` | 规范化 `[x, y, w, h]` 区域，供所有带 `region` 的接口用 |
| `matchTemplate` + `scales` | 模板缩放匹配，可抗**视野缩放**（M12） |
| `detectAndComputeFeatures` + `matchFeatures` | 特征匹配对缩放/旋转稳定，可识别固定 UI 图标或地标 |

> ⚠️ **6.8.0 起，依赖 OpenCV 的方法需要外部 OpenCV 插件**（插件中心安装 / 启用 / 授权），未装会抛插件加载异常。

### 3.4 OpenCV Hough 找圆精化（2026-09-24 新增，lib/circle-refiner.js）

**动机**：§3.1b 的面积/bbox 兜底到顶了——皮肤球彩色像素只有外圈，0.69 仍低于真值 0.93。

狗 r=214（-12%）、self 263（+5%）、绿刺 -4~-16%；与轻量径向梯度搜边精度持平。

**AutoJs6 内置 OpenCV**（org.opencv，用法参考 tasks/find-circles-overlay）：

- vision.js 加注入口 `setCircleRefiner(fn)`：**PC/冒烟不注入 → 行为与旧版完全一致**；
  手机端 main.js 注入 `lib/circle-refiner.js` 的 makeRefiner(CFG)。
- 精化链路：perceive 里 `small.mat → cvtColor(BGRA2GRAY) → GaussianBlur(3,3) →

  全局找圆后按先验匹配（圆心距 ≤ max(10ds, rArea)、半径 ∈ [0.6,2.2]×rArea，取最近）。

- 半径口径：`r = max(面积/bbox兜底, Hough)` —— 精化只增不减，Hough 偶发漏检不伤实心球；
  圆心同步精化（dx/dy 更准）。球对象新增 `refined: 1` 标记，stats 新增 `refine_ms`。

### 3.7 贴身遮挡半径下界 + 「尺寸不可信」护栏（2026-09-25，老板 6 张重叠截图定案）

**触发场景**：目标球被**自己的圆盘**盖住 ⇒ 只剩外弧可见 ⇒ 面积/bbox 都被削 ⇒ 半径偏小
⇒ `size_ratio` 被压低 ⇒「本来能吃掉我的球」被判成「我能吃」⇒ 决策层全速冲上去送死。
死亡实锤两条（同类）：2026-09-24 `death-1790251633050.jpg`（self_r528 被身边大球吃，
死前 5 帧 `n_threat=0`）；2026-09-25 真机跑局 `_calib/aim/run-0925-0017.jsonl` 第一局
f75~f83（self_r 254→189 被连啃 7 帧、`n_threat` 多为 0，f84 起 self 连丢 41 帧 → 死亡，
而死前最近球在 432px 外）。

#### 一、真值怎么量的（**这是本节最重要的方法**）

老板提供了 6 张「专门与其他球重叠」的截图（`_calib/argb/ov1..ov6`），**离线就能量真值**，
不必等真机数据：

- `_calib/silhouette.py`：非背景掩膜（`max(R,G,B)>78 或 max−min>34`，与工程色域门**无关**）
  + 连通域 ⇒ 认出「自己+目标球」的粘连大域，作为拟合区域；
- `_calib/fitcircle.py`：在该域里**剔除自己圆盘 +8px 内**的边界点（露出来的正是目标球的
  可见外弧），RANSAC + 最小二乘**圆拟合** ⇒ 真实半径，并打印残差 RMS 与「半径比自己」。

| 图 | 目标球 | 真值 r（RMS） | 真值 ratio | 色域口径 r | 色域口径 ratio | 结论 |
|---|---|---|---|---|---|---|
| ov2 | 餐餐猫（被自己盖住近半） | **436** (6.0px) | **1.43 威胁** | 260 | 0.85 可吃 | **致命反判** |
| ov6 | 美丽鼠（被自己盖住顶部） | 284 (3.2px) | 0.91 可吃 | 276 | 0.89 可吃 | 口径正确 |
| ov3 | 餐餐猫（几乎不重叠） | 466 (5.6px) | 1.77 威胁 | 424 | 1.61 威胁 | 口径正确（-9%） |

⇒ **"欠估"确实由"被自己遮挡"触发**：同一只猫，不重叠时只低估 9%，被盖住近半时低估 40%。

#### 二、为什么不能靠几何修正（本节结论，别再试了）

先看两条**可证**的下界（`lib/vision.js#occlusionRadiusDsf`，两者取大）：

1. `max(bboxW,bboxH)/2`：球的圆盘包含全部可见像素 ⇒ 半径 ≥ 可见集在任一方向跨度的一半。
2. `(far − selfR)/2`：bbox 压在自己圆上 ⇒ 球与自己盘相交（`d < R + r`）；又 `d + r ≤ far`
   （取 bbox 四角最大，是 `d+r` 的上界）⇒ `r > (far − R)/2`。

⚠️ 而在 ov2 的猫身上，**色域口径的 bbox 本身就被削掉一大截**（512×432，真值圆 872×872）
⇒ 任何 bbox 下界都够不到 0.93 阈值（实测只到 257 ≤ 原值 260，等于没生效）。

那换个"看几何上界"的思路呢？实测过 bbox 对角/垂直跨度（`_calib/estimcmp.js`）：

| 估计量 | ov2 猫（真值 1.43，必须判威胁） | ov6 鼠（真值 0.91，必须判可吃） |
|---|---|---|
| 色域 base（现口径） | 0.85 ✗ | 0.89 ✓ |
| bbox 对角/2（几何上界） | **1.08 ✓** | **1.06 ✗ 假威胁** |
| 面积反解 `πt²−lens(R,t,far−t)=A_vis` | 161（退化 = 面积法，无用） | 191（同左） |

两例的 bbox 特征几乎一样（对角/半径比 **1.29 vs 1.29**、填充率 0.36 vs 0.45）
⇒ **没有任何只看 bbox 的几何修正能同时判对这两例**。面积反解也不灵：`far` 只能取 bbox 上界，
于是解出的 `d = far − r` 偏大、lens 项退化为 0，等价于面积法。

试过的第三条路（也否掉）：把亮面车道阈值 `vBright` 70 → 60/55/50。簇 bbox 确实变大
（512→688），但**面积几乎不变**（424→460），ratio 反而更差（0.85→0.82/0.80），
且 50 时**连自己球都认不出来**（`self=null`）——猫的灰毛落在 V≈35~55，与背景/UI 装饰同段，
色域阈值切不开。

#### 三、定案：能测准就测，测不准就别吃

1. **能测准就测**（`OCCL_COMP_*`）：走上面两条可证下界，与 `r_area`/`r_ref` 取 max。
   实测 14 张图共抬高 15 个球的半径，**无一造成假威胁**（含 ov5 `124→228` ratio0.70、
   screen_01 `134→164` ratio0.54，都在阈值内）。
2. **测不准就别吃**（`OCCL_DENY_*` → 球字段 `unreliable`）：**轮廓不完整**（bbox 填充率
   < `OCCL_DENY_FILL_MAX`＝0.5，与 `SKIN_FILL_MAX` 同口径：多色皮肤球的白/灰体表大面积
   过不了色域门）**且** bbox 压在自己圆盘上 ⇒ 决策层**不许把它当追吃目标**（`lib/aim.js`
   跳过并记进 `eat_denied`，原始 `edible`/`threat` 照旧如实算，便于复盘）。

**实测代价（14 张图 338 个球）**：被护栏改判（原判可吃 → 不吃）**9 个**，全部是
"皮肤球 + 贴在自己身上"；其中 7 个 ratio < 0.6（本就很少会成为最大 `r/gap` 的追吃目标，
实际损失更小），2 个是 ov2 的猫（0.85）与 ov6 的鼠（0.89）。
**收益**：ov2 这类「真值 1.43 却被判可吃」的致命反判被挡住。

> ⚠️ **触发门也修了**：旧版用 bbox **四条边中点**的最近距离判"是否与自己圆盘相交"，
> ov2 猫的边中点最近 341 > selfR 306 ⇒ 判"不相交"直接跳过补偿（该触发的场景整类没触发）。
> 现在用真正的点-矩形距离（`bboxNearDist`），ov2 猫的矩形最近点 151 < 306 ⇒ 正确触发。
> 冒烟 H1 专门钉这个回归（构造"角贴圆、边中点都在圆外"的例子）。

#### 四、仍然残留（下一轮的靶子）

1. **皮肤球白/灰体表仍抓不全**（本节最根本的洞）。当前只做到"不误吃"，**做不到"量准"**。
   可行的下一步：**边缘/圆拟合路线**——手机端已有 OpenCV Hough（`lib/circle-refiner.js`），
   它跑 Canny 边缘、不依赖颜色，理论上能把猫的外圈（紫环 + 灰毛边界）拟出来；
   但当前只对 `rArea ≥ EDGE_REFINE_MIN_R(56屏)` 的簇做、且匹配窗口是 `[0.6, 2.2]×rArea`
   ⇒ **被遮挡时先验半径本身偏小，窗口也就跟着偏小**，搜不到真圆。要试就把窗口按
   「可见弧长/bbox」放宽。⚠️ PC 重放**没有 OpenCV** ⇒ 这条只能在真机上验。
2. **同色串珠会污染 self 的 bbox**：ov2 的 self 簇 area 1530（≈ r306 实心盘，正确），
   但 bbox 却是 1096×1136（真盘应为 612×612）⇒ 紫色彩豆/描边沿一条链被并进 self。
   `area`/`cx` 仍可信，`bbox` 不可信 —— 凡是要用 self 的 bbox 的算法都得记住这条。
3. **护栏默认"全拒"**，未按 ratio 再收一道（本可只拒 ratio ≥ 0.6 的，省掉 7 个小球的损失）。
   留作调参项：`OCCL_DENY_FILL_MAX` 调小即可收紧，或后续加 `OCCL_DENY_RATIO_MIN`。
   （2026-09-25 真机实测：22 次触发全部贴脸、零假阳性，见 `bb-真机跑局诊断-20260925-0104.md` §3。）
4. **腿① 的生效情况目前观测不到**（2026-09-25 真机实测确认）：`occl_boost`/`occl_unreliable` 只写进
   `state.stats`，而 `main.js` 读 `state.stats` 时只取 `frame_ms/resize_ms/getpx_ms/scan_ms/runs/hits`
   ⇒ 这两个计数**是死字段**，日志里恒为 0 次出现；`snap()` 也不输出 `r_occl`。
   要判"遮挡补偿有没有生效/有没有过度补偿"，必须先补这两处出口（纯日志改动）。
