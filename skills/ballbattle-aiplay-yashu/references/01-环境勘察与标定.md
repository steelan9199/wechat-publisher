### 悬浮条（HUD）口径 —— 老板唯一的人眼判据（工程 0.6.6 起）

`HUD_DEATH_HOLD_MS`（判死确认后悬浮条停留时长，默认 **1500ms**；纯显示、期间零输入）。

#### 取法（三步，全部走 `autojs-mobile-automation-yashu`）

**前提**：手机已进无尽模式、横屏、屏幕点亮；中继活着（`curl -s http://localhost:9421/health` → `"phone":"connected"`）。

1. **起测量悬浮窗**（长任务，`--wait 0` 立返 taskId）：
   ```bash
   node scripts/run-task.js qiu-btn-measure --args '{}' --wait 0
   ```
2. **手机上对齐并保存**：点目标名（`摇杆` → `吐孢子` → `分身`）→ 拖 1px 红圆环粗调 →
   用步长档（1/5/10/50）配上下左右键、`±半径` 键精调 → 点「保存」。三个都量完点「关闭」。
   - 想验证量得准不准：把「穿透」点开（触摸还给游戏），按测得坐标点一下按钮看游戏反应，验完点回「穿透」关。
   - 半径按**实际可触发范围**对齐——按钮有外发光/描边时，别只对齐内圈图标。
3. **读回 / 校验**：
   ```bash
   node scripts/run-task.js qiu-btn-read --args '{}'
   ```
   → `{ok:1, count:3, expected:3, ready:1, missing:[], screen:{w,h,rot}, list:[{name,cx,cy,r,rot,ts,rotMatch},...]}`

**判据（缺一不可）**：`ready: 1` **且** 每个目标 `rotMatch: true`。
`missing` 列出还缺哪个目标；`ready: 0` 就回去补量，**不许拿半套数据硬跑**（`hydrateButtons()` 在启动时也会拦）。

## 四、色域标定（感知的地基）

**为什么必须标**：识别依赖颜色分割，而不同手机屏幕、不同游戏主题（皮肤/活动）会导致颜色偏移。**换设备或游戏大版本更新后必须重标。**

> **本节的数值已于 2026-09-23 标定完毕**，输入为 `D:/empty/手机截图/screen_01..05.jpg`（5 张 3200×1440 真机截图）。

> ### ⚠️ 口径三条（先读，否则阈值必错）
> 1. 本节数值一律是**运行时口径** = `lib/vision.js` 的 `rgbToHsv()`：**H∈[0,360]、S∈[0,100]、V∈[0,100]**。
>    `config.js` 的 `HSV_SELF` / `HSV_BALL` / `HSV_BG` 也必须是这个口径——`inRange()` 直接拿它比。
> 2. 它与 **OpenCV 口径**（`cvtColor(BGR2HSV)`：H∈[0,179]、S/V∈[0,255]）**不同**。换算：
>    `H_rt = H_ocv × 2`　`S_rt = S_ocv / 255 × 100`　`V_rt = V_ocv / 255 × 100`
>    用 Python/OpenCV 复算本节数值时**必须先换算再比对**，否则会得到一套错误但"看起来合理"的阈值。
> 3. 感知层不调 `images.cvtColor`（那是 OpenCV 口径），全程用 `images.pixel()` 取 ARGB 再手算——所以只有运行时口径有意义。

| UI 紫色图标 | 6 | 105 – 341 | 6 – 10 | 由 UI 屏蔽带挡掉（全在 x≥2500 带内） |
| 散落噪点 | **115** | 11 – 97 | 2 – 6 | **必须滤掉**——纯色底上抖动出来的孤立小点 |

> **面积下限取 `≥800 px`（等效半径 ≥16px）**：距最小真实碎片（1936）留 2.4 倍余量，同时把噪点（≤97）整段滤掉，中间留出 8 倍空档，安全。
> 该下限由 `vision.js` 的 `clusterRuns()` 里的 `area` 门槛承担；若后续发现自己球被切碎漏检，**先降 SCAN 门槛而不是降这个面积下限**。

### 4.2.2 判据验证结果（2026-09-23）

用面积 ≥100 的连通域在 5 张图上做全量验证，逐块判断「是否落在 `SELF_SEARCH_RADIUS` 内 **或** UI 屏蔽带内」：

| 图 | 命中块数 | 落 ROI | 落 UI 带 | **漏网** |
|---|---|---|---|---|
| screen_01 | 1 | 1 | 0 | 0 |
| screen_02 | 7 | 7 | 0 | 0 |
| screen_03 | 1 | 1 | 0 | 0 |
| screen_04 | 2 | 2 | 0 | 0 |
| screen_05 | 19 | 13 | 6 | 0 |
| **合计** | **30** | 24 | 6 | **0** |

> 顶部 UI 带取 `y ≤ 200` 与 `y ≤ 340` 两种口径都得到 0 漏网。**取 `y ≤ 200`**——更窄，给自己球长大后（半径 >288）留更多空档。
> screen_02 那 7 块里有 6 块是面积 103–560 的碎块，实为**同一颗球被右下角绿色刺球遮挡**切出来的（都在球体内部），不是分身——这正是「自己 = 一组同色碎片」契约的由来，聚合时必须把它们并回一颗。

#### ⚠️ 关于「紫是不是自己独有」（已实测解答）

> 用户口径是「紫非独有」。实测结论更精确：
> - 用**严格域**（判据 1）扫 5 张图，除自己球外，**没有命中任何一颗其他玩家的球**。画面里那些显眼的紫球实测 **H≤268、S/V 明显更低**（screen_05 里其余紫像素 S 中位仅 ≈58、V 中位 ≈68），落在域外。
> - 唯一的假阳性是**右上角排行榜的紫色 UI 图标**（screen_05 里有 5 个这样的块，最远距屏幕中心 1386px）——用判据 3 屏蔽即可。
> - **因此：颜色可以作自我主判据，但必须叠加中心区 ROI + UI 屏蔽**，不能只靠颜色全区扫描。
> - 若日后遇到某皮肤/活动导致真球撞进严格域，二级校验是**「被橙环包裹」**（判据：紫连通域外接框内存在闭合橙环，且环面积 ≪ 实心面积）。注意橙色**本身**不独有——screen_03 里就有一颗其他玩家的实心橙色大球。

### 4.3 UI 屏蔽带（`UI_MASK_RECTS`）

实测高饱和像素在屏幕上的分布（16×9 网格密度图）显示，固定 UI 集中在**顶部带**与**右侧带**。

⚠️ **本条 2026-09-24 深夜已两次改版，当前口径见下（务必以 `config.js` 为准）**：

| 矩形 `[x, y, w, h]` | 覆盖什么 | 处理方式 |
|---|---|---|
| `[0, 0, 3200, 200]` | 顶部积分条（`吞噬积分`）、`录屏中`、灾难免死倒计时、延迟图标 | **硬裁**（`uiClip` → `yStart`） |
| `[2580, 195, 620, 465]` | 右上排行榜（含金皇冠/名次章/白字/底部"观战人数"，实测面板到 y≈645） | **无彩色簇区**（`dropUiAchroma`） |
| `[1700, 120, 270, 150]` | 吞噬积分面板（白字/白边，8/8 图固定出现） | **无彩色簇区** |
| 摇杆 `457,964 r231` / 吐孢子 `2817,541 r160` / 分身 `2494,1203 r155` | 三个圆形按键 | **无彩色簇区**（几何由手机 storages 经 `setStick/setUiButtons` 注入，不进本文件） |

> - **为什么不再硬裁**：硬裁会连带削掉**压在 UI 底下的真球**——实测吐孢子方框把右上巨球削掉
>   16% 面积，ratio 从 1.03（威胁）掉到 0.89（误标可吃）。改"质心落在区内 **且** 无彩色才丢"后，
>   彩色真球连被压住的部分也完整保留。
> - **为什么不是"全高条带"**：旧值 `[2500,0,700,1440]` 被 `uiClip` 翻译成 `xLimit=2504`
>   → **屏幕右侧 700px 全高盲区**，右侧逼近的威胁全部隐形（screen_03 实锤）。
> - 自己球恒在屏幕中心、半径 ≤290 —— 顶部带**永不与自己球重叠**。
> - 带内 UI 元素随**游戏版本**变化。改版后若发现新的误判簇，用同法（网格密度图）定位并补矩形，
>   **当轮落盘**。

### 4.4 其他球：反向定义（不枚举颜色）

球球大作战的球**颜色随机**，无法枚举。定义（2026-09-24 深夜改「两车道」，见 `02` §3.6）：

```
其他球候选 = ( V ≥ 42 ∧ ( S ≥ 45 ∨ V ≥ 70 ) ) ∧ ¬自己球严格域 ∧ ¬(落在 UI 区内 ∧ 整簇无彩色)
             ↑ 彩色车道 或 亮面车道（白/奶油/浅色球）
```

实测支撑：旧口径（全图 S≥45 ∧ V≥42）像素占 3–12%，其 H 覆盖 0–360 全环（峰值落在橙黄 26–46°、
黄 68/90°、绿 116–128°、青蓝 206°、红 0–12°/352–358° 一带）；**V<42 的彩色像素仅占 0.4–1.1%**，
故 V≥42 是安全下界（背景 V=22、网格线 V≤32，均被排除）。
**新增亮面车道后实测**：V≥70 ∧ S<45 的像素绝大多数是**真球体表**（白球、白皮肤球、暗绿鲜来了），
8 图新增可吃物 26 个，UI 幻影 0 个（详见 `02` §3.6）。

> 候选里混有**球体皮肤、特效、描边**，以及大量**非圆形的食物与道具**。
> **实测（放大 screen_05 顶部画面逐像素核对）**：可吃目标里同时存在绿色**三角**、蓝色**方块**、粉色**五边形**、紫色**刺球**、黄色**包子形** —— 形状五花八门。
> ⛔ **所以「圆形度」不能用作筛选条件**（此前的假设已删除）。可用约束只有：**面积下限、颜色（§4.1）、与自己球的距离、是否落在 UI 屏蔽带内**。
> 其中**自己碎片的面积下限已实测**（§4.2.1，≥800px）；**其他球与食物的面积下限仍未实测**——游戏里的小彩点（食物、孢子）本来就该被吃掉，下限设高了会把食物漏掉。需真机对着画面量一次食物尺寸再定。

### 4.5 换设备 / 游戏改版后的重标方法

1. 进入无尽模式，截 **5 张**图：至少 1 张"自己球未分身的大球"、1 张"分身成多碎片"、1 张"画面球多"。
2. 用本节同法（全图低饱和 V 分布 + 严格紫连通域 + 网格密度）重跑，**先验证判据 1、2，再验证判据 3**。
3. 判据通过的标准：严格域命中的连通域**全部**满足「距中心 ≤`SELF_SEARCH_RADIUS`」或「落在 UI 屏蔽带内」。
4. 结论双写进本节与 `config.js`（`HSV_SELF` / `HSV_BALL` / `HSV_BG` / `UI_MASK_RECTS` / `SELF_SEARCH_RADIUS`），版本号 patch +1。

- 游戏镜头**跟随自己的球**，因此自己的球在屏幕上位置基本固定。

### 5.1 自己球位置（已实测）

5 张真机图上，自己球（多碎片时为**整组加权质心**）与屏幕几何中心 `(1600, 720)` 的偏差：

| 图 | 形态 | 质心 | 距中心 |
|---|---|---|---|
| screen_01 | 单球 R=288 | (1599, 718) | **2 px** |
| screen_02 | 单球 R=268 | (1589, 696) | 26 px |
| screen_03 | 单球 R=242 | (1587, 728) | 15 px |
| screen_04 | 分身 2 球 R=214/209 | (1595, 724)（组质心） | **4.5 px** |
| screen_05 | 分身 13 碎片 R=25–65 | 各碎片距中心 ≤438 px | — |

| 参数 | 值 | 说明 |
|---|---|---|
| `SELF_SCREEN_X` | `1600` | = 屏幕中心 x。实测偏差 ≤26px，**不是硬编码猜的** |
| `SELF_SCREEN_Y` | `720` | = 屏幕中心 y |
| `SELF_POS_FIXED` | `true` | 横屏 + 本设备 + 5 张图全部验证成立；**分身时按"组质心"而非单球质心读** |

| `SCALE_REF_RADIUS` | `288` | 基准帧（screen_01）实测自己球半径，仅作记录 |
| `SCALE_K` | `placeholder` | **仍未标定**——需要"同一局内两种体型 + 一个游戏内距离参照"才能反推 |

**验证方法（换设备后重做）**：先用一张标定图定出质心位置与半径基准；然后在游戏中吃几个球变大一档，再截一张图，看半径变了多少、同距离的球像素距离变了多少，反推缩放关系。
**未验证以前，快循环一律用「屏幕像素相对位移」决策，不做游戏单位换算**——这样即使缩放标不准，也能先跑起来。
