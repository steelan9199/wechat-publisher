## 一、线程与节拍模型

```
主线程（快循环，~TICK_MS 一轮）
  captureScreen → perceive → computeAim → pushStick
        ▲                                    ▲
        │ 读 latestState(原子替换)            │ 读 latestPolicy(原子替换)
        │                                    │
子线程（慢循环）threads.start                │
  sleep(SLOW_TICK_MS) → callJev(state) → translate → 写 latestPolicy

子线程（按键线程）threads.start  ← 2026-09-24 新增
  轮询 clickQ 队列 → press(按键坐标, CLICK_PRESS_MS)   // 吐孢 / 分身，与摇杆手势并行
```

**三条硬规则**：

1. **主循环里不许有阻塞网络调用**——`http.postJson` 同步执行会卡死整帧。
2. **线程共享只走「整体替换」的单一变量**（如 `latestPolicy = newObj`），不做原地修改，避免读写竞争。
3. `threads.start` 里的异常**不会被外层 try/catch 捕获**（见 autojs 技能编码细则），子线程内部必须自带 try/catch。

### 1.1 ⭐ 注入分工总表（用户 2026-09-24 定案，**本节为权威口径**）

> 原问题：`press` 与摇杆手势会不会互抢指针？—— **答案是"分场景用不同 API"，不是"想办法让两者共存"**。

| 场景 | 用什么 | 说明 |
|---|---|---|
| **只想单独点某个按键**（吐孢 / 分身，且**不与摇杆同时**） | **`press`** | 用户原话："如果你只是想吐孢子，或者只是想单独点击某个按键，那么你就用 press" |
| **要同时按多个（多指并发）**（＝**边移动边喂球**：一根手指推摇杆 ＋ 一根手指点吐孢） | **`gestures` / `gesturesAsync` 一次调用里放【多个笔画】** | 用户原话："如果你要同时按多个按键，那么你就使用 `gestures([...], [...], ...)`" |

- **多指并发的写法**（每个笔画＝**一根独立手指**，互不为同一指针 ⇒ 从根上不互抢）：

```javascript
// 笔画格式：[startTime, duration, [x,y], ...经过的点]
gesturesAsync(
  [0, STICK_MOVE_MS, [cx, cy], [tx, ty]],          // 手指①：摇杆，从圆心拖到目标偏移点
  [400, CLICK_STROKE_MS, [SPIT_X, SPIT_Y]],        // 手指②：吐孢第 1 下
  [600, CLICK_STROKE_MS, [SPIT_X, SPIT_Y]],        // 手指③：吐孢第 2 下（靠 startTime 错开）
  [800, CLICK_STROKE_MS, [SPIT_X, SPIT_Y]]         // 手指④：吐孢第 3 下
);
```

- ✅ **已真机实测（2026-09-24，用户目视）**：上面的形式（摇杆笔画按住 2s ＋ 5 个吐孢笔画错开 400~1200ms）⇒ **球在动、孢子也吐出来了**，多指真并行、不互抢（`TBD-25` 结案）。
- ⚠️ **按键笔画的 `duration` 用 50ms，不要用 1ms**：1ms 在"单发 `press`"场景已验证可行，但在**多笔画流**里事件太短、更易被系统合并或丢弃。
- **同一位置多次点击** ⇒ 靠**多个笔画 + 不同 `startTime`** 实现（每个笔画＝一根独立手指），不是在一根笔画里写重复点。

- ⛔ **旧方案已作废**：~~"摇杆走 `gesturesAsync` ＋ 按键走 press 线程，两路并行"~~ —— 那是**两条注入流各自抢指针**，正是 §6.7 那条头号未结项的风险源。
  ⇒ **并发一律收敛进「一次 `gesturesAsync` 的多个笔画」**，由 AutoJS 统一编排多指，不要自己开两条流。
- **主循环里用 `gesturesAsync`（非阻塞）**；`gestures` / `gesture` / `press` / `swipe` 都是**阻塞**的，放进主循环会卡死整帧。
- **单指时仍走 `press`**（用户硬要求）；`press` 阻塞 ⇒ 放**按键子线程**（见 §一 线程图与 §6.4）。
- `delay` 可省略（默认 0）；同一调用里给不同 `delay` 即可编排**错时**多指。

## 二、摇杆按压：抢占式重发

> ⚠️ **本节原前提已被证伪（2026-09-24）；新架构已具备前置条件，待用户点头后改造**
> 旧前提是"摇杆必须**一直按住**才走"，故必须周期性重发。已确认**不成立**：摇杆输入是**绝对位置**（参考原点恒为圆心），且**方向与速度被锁存**（抬手后钮视觉回中、运动照旧）—— 见 `00` **M14**。
> ✅ **两个前置条件均已结案，且已真机实测复核**（2026-09-24）：
> ① 注入端**同样锁存**（`00` `TBD-21`）；② **一次输入即可设定方向＋速度**（`00` `TBD-23`）。
> **实测**：`gesturesAsync([0, 300, [457,964], [457,1195]])` 发**一次**后彻底停手 ⇒ **球持续向下走不停**；用户原话"除非你点一下屏幕中心，它才会停止"（`00` M14）。
> ⇒ **"保持移动"不依赖持续按压**；**一次输入 = 设定 + 锁存**，既不用拖动、也不用重发。
> ⇒ **停止方式唯一**：下发一次**偏移＝0**（圆心）的输入。
> ✅ **「`press` 与摇杆手势互抢指针」这条头号风险已解决，且已真机实测**：并发场景改用「一次 `gesturesAsync` 多笔画」（每笔画一根独立手指），见 **§1.1**。
> 实测 2026-09-24：摇杆笔画 ＋ 5 个吐孢笔画并行 ⇒ **球在动、孢子也吐出** ⇒ 「边移动边喂球」**已验证可用**（`TBD-25` 结案）。
> ✅ **已改造为「换向才发一次」**（离屏式，2026-09-24 用户点头后落地）：`lib/control.js` 的 `push()` 已重写，
> 旧的"每帧抢占式重发 + 从手指当前位置起笔"**已删除**（它在新语义下会让位移趋零，见下方 §2.4）。**本节标题的"抢占式重发"已名存实亡，保留作历史入口。**
> ✅ `TBD-24`（`press` 型式是否也能用）**已降级为非阻塞** —— `gestures` 型式已实测可用，改造直接用它，不必等 `TBD-24`。

**✅「换向才发一次」已实现（2026-09-24 用户点头后落地）** —— 见 `lib/control.js#push`、`#bucketKey`。下面是要旨，代码已按它写好：

```javascript
// push(dir, speed)：只在【方向与速度档位变化】时下发一次
var key = dir.x + "," + dir.y + "," + speedBucket;     // 量化，避免抖动导致频繁重发
if (key === lastSentKey) { return; }                    // 没变 ⇒ 什么都不发（方向已被锁存）
lastSentKey = key;
// 起点 P = 按下点 = 本次原点；终点 = P + 偏移（偏移的方向=方向，长度=速度）
var px = STICK_CENTER_X, py = STICK_CENTER_Y;           // 用圆心作 P，理由见下方第 1 条
var tx = px + dir.x * STICK_MAX_RADIUS * speed;
var ty = py + dir.y * STICK_MAX_RADIUS * speed;
gesturesAsync([0, STICK_MOVE_MS, [px, py], [tx, ty]]);  // ⛔ 必须是【拖动】笔画
```

1. **起笔点 P 任意（只要在屏幕左侧区域）** —— 因为原点是"手指第一次触碰的那个点"（`00` M14），**不是**固定圆心。
   ⇒ 实际取**摇杆圆心**作 P，理由是它四周留得出 `r=231` 的空间，保证"P + 最大偏移"仍在可操作范围内；**不是**因为机制要求。
2. ⛔ **必须是带移动的拖动笔画**。**单击（含 `press` 到偏移点）不能设定方向** —— 已实测（球停住时单击偏移点，球不动，`00` M14 / `TBD-24` 结案）。
   ⇒ **禁止**用 `press(偏移点)` 当"设定方向"用；`press` 只用于**点圆心停止**、以及右侧按键。
3. **速度 = 手指离按下点的距离**（推子式，不是滑动快慢）⇒ `STICK_MOVE_MS` 只影响"手指滑过去"的耗时，**不影响最终速度**；建议 100~300。
4. ⛔ **不要走往返路径**：中途把手指移回 P ⇒ 位移归零 ⇒ 球会停。
5. **停止** ⇒ `press(圆心, 1)`（已实测），或发一次零位移笔画 `[0, STICK_MOVE_MS, [px,py], [px,py]]`。
6. **多指并发**（边移动边吐孢）⇒ 把按键作为**同一调用里的第二个笔画**，见 §1.1。右侧按键不在摇杆区，不会干扰摇杆（`00` TBD-27）。
7. ⚠️ 改造后**必须**保留 `lastSentKey` 之类的本地状态：方向锁存在**游戏侧**，脚本不能靠读图反推（见 `05` §3.1）。

**机制前提**（2026-09-24 更正）：AutoJS 的手势 API 是"发一次、走一段"，而**摇杆输入被锁存** ⇒ 抬手后方向照旧（**钮的视觉回中不代表停止**），重发**不是"维持移动"的必需**，只在**方向/速度变化**时才有意义。
✅ **输入口径已结案**：**相对位移**（`00` `TBD-22`）—— 原点 = **手指第一次触碰屏幕的那个点**；认的是"移动了多少"，**不是**"落点在哪"。

**做法**（现役实现：`lib/control.js#push`，参数取自 `config.js`）：

```javascript
// ⛔ 旧实现已删除：var cur = fingerNow(); ... [0, MS, [cur.x, cur.y], [tx, ty]]
//    它在"相对位移"语义下位移会变成 (dir − lastDir)·r ⇒ 同方向重发时球会停（见 §2.4）
var px = STICK_CENTER_X, py = STICK_CENTER_Y;   // 起笔点【固定】= 本次原点
var tx = px + dir.x * STICK_MAX_RADIUS * speed;
var ty = py + dir.y * STICK_MAX_RADIUS * speed;
gesturesAsync([0, STICK_MOVE_MS, [px, py], [tx, ty]]);   // ⛔ 必须是【拖动】笔画
// 吐孢/分身**不在这里**：单发走 press 线程（§6.4）；与摇杆同时 ⇒ 同一调用的第二个笔画（§1.1）
```

- 用 `gesturesAsync`（**非阻塞、多指**）；`gesture`/`press`/`swipe` 都是**阻塞**的，放进来会把主循环卡死。
- **注意分工（口径已更新 2026-09-24，以 §1.1 为准）**：
  - **单独点按键**（不与摇杆同时）⇒ `press` + 按键子线程（见 §一、§6.4）—— 用户硬要求。
  - **与摇杆同时按**（多指）⇒ 按键也做成**同一 `gesturesAsync` 调用里的一个笔画**（见 §1.1）。
  - ⚠️ 旧注记"把按键做成 `gesturesAsync` 零位移笔画＝手势模拟点击、不是 `press`，已删" —— **该删除针对的是"用笔画替代 press 的单点场景"**，
    **不适用于多指并发场景**：并发时用户明确要求用 `gestures` 多笔画，此时按键笔画就是正确写法。两者不矛盾，按 §1.1 分场景取用。
- **⭐ 输入口径（2026-09-24 第五次澄清，已二次修正）**：**相对位移，原点 = 手指第一次触碰屏幕的那个点**（`00` M14 / `TBD-22`）。
  - ⚠️ 同一天早些时候曾定案为"**绝对位置**、原点恒为固定圆心" —— **该表述已被修正**。两者只在"按下点＝圆心"时数值相同；真正的规则是"**认位移、不认落点**"。
  - ⇒ **起笔点 P 可以是屏幕左侧区域的任意位置**（摇杆视觉位置会跟着 P 跑）；终点 = `P + 偏移`，**偏移的方向＝方向、长度＝速度**。
  - ⇒ 旧写法"起点取手指当前位置"**依然不成立**（它假设要继承上一次落点，实际每次按下都重新定原点）。
  - ⚠️ 旧归因"每帧都从圆心重发 ⇒ 穿过中心死区 ⇒ 推进力一顿一顿" —— **现象是真的，但归因错了两次**，真因见 **§2.4**：
    是"**起笔点漂移**"（起笔点取的是上一次手势的终点）让位移变成 `(dir − lastDir)·r`，同方向时趋近 0。
- `STICK_MOVE_MS`：**只影响"手指滑过去"的耗时**，**不影响速度也不影响能走多久**（速度由位移距离决定、方向已锁存）。取 100~300；过小可能被系统合并事件。
  ⚠️ 旧写法"取 `TICK_MS` 量级以保证两次之间不出现松手空档" —— **该理由已作废**：抬手不会中断移动（`00` M14），不存在"空档"问题。

### 2.2 悬浮窗的 x 偏移：只影响悬浮窗，不影响控制

横屏下 `floaty` 窗的 `setPosition` —— **y 精确，x 恒定偏 +137px**：`setSize(3200,1440)+setPosition(0,0)` 实测落在 `(137,0)`，全屏窗实际覆盖 `x∈[136,3199]`；四下 `setPosition(0/2780, 0/1020)` 实测一律 `(137/2917, 0/1020)`，偏移与目标无关、是常量。

- ⇒ **标定/自检类悬浮窗若按屏幕坐标落位，必须先 `getLocationOnScreen` 量偏移再补偿**。`qiu-calib` / `qiu-btn-measure` 本来就是拖拽取 `getRawX()` + `getLocationOnScreen`，所以**标定数据本身没被这个偏移污染**。
- ⇒ **它不会影响控制**：所有手势走 A11Y，与悬浮窗不是同一条通道（见 §2.1）。

### 2.3 历史失效模式：摇杆中心常量没填 ⇒ 摇杆跑到左上角

旧 `config.js` 把 `STICK_CENTER_X/Y` 当**手填常量**、默认 `0`。一旦没填就开局，`push()` 发的是
`gestureAsync(HOLD, [0,0], [0,0])` —— **手势起点 = 屏幕左上角 (0,0)**，游戏据此把摇杆渲染在左上角。
与用户原话「你的摇杆都跑到左上角去了」完全吻合（*最可能原因，症状吻合但未复现验证*；不是坐标系错）。

**已结构性堵死**：三键坐标不落代码，启动时 `hydrateButtons()` 从手机端 storages `qiu-btn` 读回，
读不到就直接 `assertCalibrated()` 抛错拒绝启动（见 `config.js`）。

✅ **机制解释已补齐（2026-09-24）**：摇杆的**原点 = 手指第一次触碰的点**、且**视觉位置会跳到该点**
（`00` M14）⇒ 起点 `(0,0)` 让游戏把 `(0,0)` 认定为圆心，摇杆自然画到左上角。不再只是"症状吻合"。

✅ **首跑（t0924_035916）已定罪（2026-09-24）**：真凶是 **require 实例分裂**——control.js 的
`require("../config")` 与 main.js 的 `require("./config")` 不是同一实例，hydrate 只灌了 main 那份，
control 那份按键几何全 0 ⇒ 每笔手势发往 `(0,0)` ⇒ 圆盘锚死左上（guard 日志实证）。
详见 `05` §3.4；修复 = 依赖注入 `control.init(conf.CFG)` + push 硬闸（v0.5.0）。

### 2.4 历史失效模式：起笔点漂移 ⇒ 同方向重发时球会停（2026-09-24 定位并修复）

**症状**：球"一顿一顿"、有时干脆不走。

**真因**（在"相对位移"语义下才看得出来）：

| | 旧实现 | 游戏实际算出的位移 |
|---|---|---|
| 起笔点 | `fingerNow()` = **上一次手势的终点** `圆心 + lastDir·r` | 原点 = 起笔点 |
| 终点 | `圆心 + dir·r` | — |
| **位移** | 期望 `dir·r` | **`(dir − lastDir)·r`** ❌ |

⇒ **同方向连续重发时 `dir ≈ lastDir` ⇒ 位移 ≈ 0 ⇒ 球停住**。每 100ms 重发一次，等于每 100ms 把速度清零一次。

**为什么旧模型下"看起来没问题"**：旧模型认为"落点相对**固定圆心**的偏移决定方向" ⇒ 只关心终点，
起笔点在哪都无所谓。语义改成"相对位移"后，起笔点成了原点，**这个假设当场失效**。

**修法**：起笔点**固定**为摇杆圆心（`push()` 已改），位移恒等于 `dir·r·speed`；并改成"**换向才发一次**"。
⇒ 一举同时解决"顿挫"与"每帧重发的浪费"。

## 三、本地几何（基线策略）

> **实现位置（2026-09-25 起）**：合成逻辑在 `lib/aim.js#decompose`（**纯模块、零 AutoJs6 依赖**，
> 可在 Node 离线冒烟：`node verify/pc/qiu-aim-smoke.js`）；归一化与平滑仍在 `lib/control.js`
> （`normalize`/`smooth` 唯一实现，不复制进 aim.js）。
> `lib/aim.js` 另外吐一份**向量分解快照**（决策层可观测性），见 §3.6。

### 3.1 目标打分（追吃什么）

```
gap      = dist - self.r - ball.r            // 表面间距，越小越近
value    = ball.r / max(gap, MIN_GAP)        // 越大越值
```

取 `edible === true` **且 `unreliable !== 1`** 中 `value` 最大者 → `dirEat`。

> **★护栏前置（2026-09-25，见 §3.6.1）**：`unreliable===1` 的球即使 `edible=1` 也被**排除在追吃候选外**
> （转记 `eat_denied`）。理由：贴身遮挡下它的半径测不准，"看着可吃"可能是致命反判。这是**喂给打分前的过滤**，
> 不是打分规则本身——所以调 `EAT_RATIO_THRESHOLD` 改不动它。

**为什么用 gap 而不是圆心距**：球越大，圆心距越不能反映真实接近程度。用表面间距才不会"盯着一个大球觉得还很远"。

### 3.2 威胁闪避

```
closing  = 威胁球速度在连线方向的投影（无速度时用 1 兜底）
ttc      = gap / max(closing, EPS)           // 预计相撞帧数
danger   = 1 / max(ttc, EPS)
```

取 `threat === true` 中 `danger` 最大者 → 反方向 `dirAvoid`。

### 3.3 边界回避

```
dEdge = min(bounds.left, right, top, bottom)
若 dEdge < EDGE_MARGIN → 追加边界斥力向量
```

> **实现口径订正（2026-09-24 起，2026-09-25 补文档）**：代码里**不是**"生成一个指向场地中心的向量"，
> 而是**按轴斥力**——把每个轴的越界深度 `(EDGE_MARGIN − bounds.<dir>)` 累加成 `pushX/pushY`
> （左右、上下**可同时生效** ⇒ 贴角时两轴一起推），再把 `(pushX,pushY)` **归一化**后乘 `wEdge`。
> 屏幕坐标 y 向下 ⇒ `top` 近就往 `+y` 推、`bottom` 近就往 `−y` 推。
> `bounds` 语义 = 「球**边缘**到该方向场地边界的距离」（`lib/vision.js#edgeDist`），
> 不是"球到屏幕边的距离"。

### 3.4 合成与平滑

```
v = wEat·ê_eat − wAvoid·t̂_worst + wEdge·p̂_edge
v = 归一化(v)

// 平滑：与上一帧方向做插值，避免抖动导致球走 Z 字
u = normalize( LERP(uPrev, v, SMOOTH_ALPHA) )
```

`ê`/`t̂`/`p̂` 均为单位向量；权重取当前策略（`POLICY_WEIGHTS`）或 `config.js` 默认值。

| 权重 | 当前值（`config.js`，2026-09-24 定） | 调参方向 |
|---|---|---|
| `W_EAT` | `1.0` | 太小吃不到球、太高中毒般送死 |
| `W_AVOID` | `1.4` | 太低会撞大球，太高会一直逃跑 |
| `W_EDGE` | `0.8` | 太低贴边被吃，太高不敢靠近边缘吃球 |
| `SMOOTH_ALPHA` | `0.45` | 太高抖动，太低反应迟钝 |

> ⚠️ 这四项直接影响行为，改任一项必须**同一轮内**同步 `config.js`、本文档的表与 §四 的
> `POLICY_WEIGHTS` 映射（`chase`/`retreat`/`patrol`/`hug_edge` 各一套）。

### 3.5 无目标兜底

`balls` 为空或没有可吃目标时 → **沿当前方向走 / 缓慢绕圈**（`PATROL_MODE`），不要长时间原地不动。

> **⚠️ 更正（2026-09-23）**：原文写「停住 = 送死」是**过度断言**。
> 据用户：**被吃才叫死** —— 停住时若无人来吃你、或对方吃不动你，**就不会死**。
> 「停住是否安全」属**战术判断**，交由决策层（见 `00` M13）。此处只保留中性倾向：无目标时优先保持机动，而非把它当作生死红线。

> **触发条件（实现口径）**：兜底**只在合成向量恰好为零向量时**才启用
> （无候选 / 权重为 0 / 三者互相抵消），方向 = 上一帧方向 + `PATROL_TURN`。
> 判据是**零向量**，不是"没有可吃目标"——有威胁球时即使没有可吃球，也不会绕圈。

#### 3.6.1 贴身遮挡补偿与「尺寸不可信」护栏（2026-09-25）

**要堵的口子（真机死因）**：球贴着自己时被**自己的圆盘盖住** ⇒ 只剩一弯外弧可见 ⇒ 可见面积/bbox 被削
⇒ 感知半径系统性偏小 ⇒ `size_ratio` 被压低 ⇒「本来能吃掉我的球」被判成「我能吃」⇒ 脚本全速冲过去送死。
（第一局 27 秒死：`self_r` 7 帧掉 26%，啃食者 `avoid_n` 多为 0，见 `bb-真机跑局诊断-20260925-0025.md` §二。）

**两条腿（定案，证据见 `02-感知规范.md §3.7`）**：

| 腿 | 代码 | 判据 | 作用 |
|---|---|---|---|
| ① **能测准就测** | `vision.js#occlusionRadiusDsf`（config `OCCL_COMP_*`） | bbox 与自己圆盘相交时，取两条**可证下界**的较大者：`max(max(bboxW,bboxH)/2, (far−selfR)/2)`，上限 `rUsed × K` | 把被削的半径**抬回下界**，直接进入 `r` 参与 `size_ratio` |
| ② **测不准就别吃** | `vision.js#silhouetteUnreliable`（config `OCCL_DENY_*`）+ `aim.js` 护栏 | `bbox 填充率 < 0.5` **且** bbox 与自己圆盘相交 ⇒ 标 `unreliable=1` | 决策层见 `unreliable` **跳过该追吃目标**，并把它记进 `eat_denied` |

**为什么必须两条腿**：老板 6 张重叠截图（真值用 RANSAC 圆拟合量出）证明——**没有任何只看 bbox 的几何修正
能同时判对** ov2 餐餐猫（真值 ratio 1.43 威胁，被色域口径报成 0.85 可吃 ＝ 致命反判）与 ov6 美丽鼠
（真值 0.91 可吃，感知 0.89 正确，几何上界一修反而变 1.06 假威胁）。⇒ 只能"能测准就测、测不准就别吃"。

**分工（别混写）**：开关（`OCCL_COMP_ENABLE` / `OCCL_DENY_ENABLE`）**只在感知层读**，产出的 `r_occl` / `unreliable`
随球对象传给决策层；**决策层只认球上的 `unreliable` 标记，不重复读开关**（避免双写、避免两处口径漂移）。
⇒ 离线重放（`qiu-vision-replay.js`）与真机 `perceive` 共用同一份 `occlusionRadiusDsf`/`silhouetteUnreliable`，结论一致。

**实测代价**（14 张真机图离线复算）：338 个球里，护栏改判 9 个、下界抬高半径 15 个，**无一个假威胁**（即没有把本来安全的球误标成威胁）。

## 四、慢循环策略如何作用到快循环

慢循环（JEV）输出的是**离散策略**，不是方向。快循环负责"翻译"：

| 策略 | 快循环行为 |
|---|---|
| `chase` | 正常追吃（权重用默认值） |
| `retreat` | `W_EAT = 0`，`W_AVOID` 拉满 |
| `patrol` | 忽略 `edible`，只做边界回避 + 远离大球 |
| `hug_edge` | `W_EDGE` 归零甚至反向，主动靠近边缘找小球 |

**关键**：JEV 改的是**权重与模式**，不是每帧方向。这样即使 JEV 慢 500ms，球也不会因为"决策晚到"而失控。

## 六、方向与动作：分裂 / 吐孢 / 摇杆居中

**机制**见 `00-游戏机制契约.md` M10 / M04 / M13：按「分身」键 → 碎片数翻倍（1→2→4→8→16），**总体积守恒**，上限 16；**体积未达门槛分裂不了**（见 `00` §六 `TBD-17`）。

### 6.1 「大圆映射」—— 多球时摇杆的统一语义

**这是多球状态下一切"方向"动作的总规则**（分裂、吐孢、聚拢通用）：

1. 想象一个**大圆把所有碎片囊括进去** ⇒ 这个大圆就是"整组的身体"，相当于一个**放大版的摇杆**
2. 把这个大圆**缩放到与左下角真实摇杆同等大小**
3. 此时**真实摇杆指向的方向，就是碎片移动 / 飞出的方向**

- **单球**：退化为"新碎片朝摇杆方向飞出"，同一规则。
- 多球按分身时，组内各碎片**各自分裂**（如 3 球 → 6 球），新碎片方向均为摇杆指向方向。

⇒ **实现含义**：计算摇杆方向时，参照物是**碎片组的外接圆**，不是某一个碎片。摇杆向量先归一化再作用于整组。

### 6.2 摇杆居中：停驻 ＋ 向心聚拢

**摇杆居中基本上就是"停住"**（用户 2026-09-23 更正了此前"居中 ≠ 停住"的写法）。

- **单球**：居中 ⇒ 球**基本不动**。
- **多球** ⇒ **所有碎片缓慢向【碎片组外接圆的圆心】聚拢**：
  - 有**一个远大于其它的主球** ⇒ 圆心≈主球圆心 ⇒ 表现为**主球不动、周围小球缓缓靠拢**
  - **全是相近的小球** ⇒ **全体一起向圆心聚拢**
- ⇒ 实现上这是一条**自然收拢动作**：居中 = 「停驻 + 向心聚拢」，可用于**被动合球**（M05 无冷却）。
- **⚠️ 不要**再把"摇杆居中"当成需要额外开启的档位；它就是一个默认的、缓慢的收拢姿态。
- **⚠️ 也不要把"停住"等同于"送死"**（见 §3.5 更正）：被吃才叫死。
- **⭐ 居中保留朝向**（用户 2026-09-23 确认）：球停住，但**"最近一次移动方向"被保留**——**单球居中**时按**分身**，新碎片就朝这个方向飞出（与单球居中吐孢**同源**）。
  - ⚠️ `lastMoveDir`（最近一次非零摇杆方向）在摇杆归零后**不要清零**，否则居中时的方向会退化成零向量。
- **✅ 多球 + 居中按分身 ⇒ 走外接圆圆心**（用户 2026-09-23，结掉 `00` §五 `Q5`）：与吐孢**同一套口径**。
- ⇒ **总览：居中时「吐孢」与「分身」共用一个方向函数**，只按 `self.n` 分岔（判据见 6.3）。

### 6.3 吐出方向（孢子）

按**摇杆状态 × 球数**分三种情形（用户 2026-09-23 全部确认）：

| 摇杆状态 | 球数 | 孢子吐向 |
|---|---|---|
| **指向某方向** | 任意 | **该方向**（多球先走 6.1 的大圆映射） |
| **居中** | **多球** | **碎片组外接圆的圆心**（＝所有球的中心点），即「中吐」——**纯向圆心** |
| **居中** | **单球** | **「最近一次移动方向」** |

**⭐ 单球 + 居中的特例（本轮新增）**：球停住了，但**朝向被保留**——吐孢沿**摇杆上一次指向的方向**出去。
- 上次向右移动 → 居中（球静止）→ 按吐孢 ⇒ 孢子吐在**右边**；上次向上 ⇒ 吐在**上边**。
- ⚠️ **实现含义**：快循环必须维护 `lastMoveDir`（最近一次非零摇杆方向），**摇杆归零时不要清除它**；`self.n === 1 && 摇杆居中` 时吐孢用 `lastMoveDir`、不是当前摇杆向量（当前是零向量，直接用会退化成"原点方向"）。
- ✅ **两条居中子规则互不叠加**（用户 2026-09-23 确认）：**多球居中＝纯向圆心**，`lastMoveDir` **只在单球居中**生效。
- **判据（实现用）——吐孢与分身（6.5）共用同一个方向函数**：
  ```
  // 仅当摇杆居中时调用；摇杆非居中 ⇒ 方向 = 摇杆方向（多球先过 6.1 大圆映射）
  function stickCenteredDir(self) {
    return self.n > 1 ? centroidDir()   // 碎片组外接圆圆心（＝中吐，纯圆心）
                      : lastMoveDir;    // 最近一次非零摇杆方向（勿在居中时清零）
  }
  ```

### 6.4 吐孢操作：点按 vs 长按

| 操作 | 行为 |
|---|---|
| **点一下** | **立即吐出 1 颗**（无延迟；用户口述整个出孢过程 ≈ **5ms**，即"出孢瞬时"）；⭐ **单点无冷却** —— 点几次吐几颗，**速率只由点击速率决定**（用户 2026-09-24：1 秒点 100 次 ⇒ 吐 100 颗） |
| **长按** | **连续吐**；游戏需先判定"是否长按" ⇒ 约 **100ms 判定延迟**后才开始连吐（`TBD-19`），连吐**速度较快** |

- ⇒ 想要**精准投 1 颗**（如微量调体积、单发推刺）：用**点按**。
- ⇒ 想要**连续吐一串**：两种都行 —— **点按连点（无冷却，想吐多快就多快）**，或长按（要预留 ~100ms 启动延迟）。**别默认长按更快**。
- ⇒ **无冷却的真正约束是质量**：每颗都扣 `m_spore`（`TBD-8`），连吐 = **快速抽干自己** ⇒ 速率上限应由**决策层按质量预算定**，不是由游戏冷却定。
- ⛔ **速率定案：15 次/秒**（用户 2026-09-24 拍板「1 秒最多点 15 个孢子」）—— 游戏侧**超过 ~30 次/秒会被判为外挂**。任何提速实现都得先过这一关。
  ⇒ 实测（间隔 67ms × 15 次、按住 1ms、子线程）**三轮复现**：**15/15 成功**、速率 **14.7 / 14.8 / 14.7 次/秒**、起点间隔 **67~69ms（几乎零抖动）** ⇒ **该档稳定可用，已定为生产值**（`CLICK_MAX_PER_SEC = 15` ⇒ 闸门间隔地板 `ceil(1000/15) = 67ms`）。
- ⚠️ **30/s 档的产出存疑（未定论，别当成可用值）**：间隔 34ms × 30 次实测 `press` **30/30 返回 true**、起点间隔 34~37ms、速率 28.7 次/秒，但用户目视「**明显不够 30 个**」、球体积只「小了一点点」。
  三种可能**尚未区分**：① 系统在 34ms 档丢事件 ② 质量见底吐不出 ③ 肉眼数不准（孢子秒被吃）。
  ⇒ 查清前**不采用 30/s**。要定论得做一个"**可精确计数**"的对照实验（见 §6.7）——目视数 1 秒内的孢子不可靠。

**⭐ 实现方式（2026-09-24 定案 + 真机实测，见 `lib/control.js`）**

- 点击一律用 **`press(x, y, duration)`，不用 `tap` / `click`**（用户硬要求；官方文档亦注明「某些情况下 tap 点击无反应」）。
- `press` 是**阻塞**的 ⇒ 按键**不进主循环、也不拼进手势笔画**；单起 `clickLoop` 线程轮询 `clickQ` 队列下发，`spit(n)` / `split(n)` 只**入队**、不阻塞调用方。
  ⇒ 队列满（`CLICK_QUEUE_MAX`）时丢新请求并计 `clickStats.dropped`——**dropped > 0 = 策略层吐得比红线允许的还快**，要回头查决策层。
- **真机实测（2026-09-24）**：

  | 场景 | 结果 |
  |---|---|
  | 按住 **30ms** ×3 | press 仅 **1/3** 返回 `true` ⇒ 返回值**不可当判据**（见下方 ⚠️） |
  | 按住 **80ms** ×3 | press 3/3 返回 `true` |
  | 按住 **80ms** ×8、**子线程**内、间隔地板 34ms | 8/8 成功；实测相邻起点间隔 **82 / 83ms** ⇒ 该档 ≈12.2 次/秒 |
  | 按住 **1ms** ×3、间隔 600~700ms、**游戏侧目视计数** | press 3/3 返回 `true`，**游戏实际吐出 3 个孢子**（用户确认）⇒ **1ms 有效** |
  | 按住 **1ms** ×15、间隔 **67ms**、**子线程**内（**三轮复现**） | **15/15 成功**；起点间隔 **67~69ms** ⇒ **14.7 / 14.8 / 14.7 次/秒** ＝ **采用值** |
  | 按住 **1ms** ×30、间隔 **34ms**、**子线程**内 | `press` **30/30 成功**、间隔 34~37ms、速率 28.7/秒；**但用户目视"明显不够 30 个"** ⇒ 产出存疑，见上 ⚠️ |
  | 按住 **1ms** ×1、落点＝**摇杆圆心** `(457,964)`、**球正在移动中** | `press` 返回 `true`；**移动中的球随即停住**（用户 2026-09-24 目视确认、"符合预期"）⇒ ① **`press` 对摇杆区同样生效**（此前只验证过吐孢按钮）；② **按圆心＝停止移动**，与 §6.2「居中＝停驻」一致 |

- ⚠️ **`press` 的返回值只作诊断，不是"游戏有没有响应"的判据**。实测按住 30ms 时返回值不稳定，但按住时长与返回值并非简单线性关系；判定"这点位/这参数能不能用"**只认游戏侧真机观察**（吐了孢子才算）。别因为一次 `false` 就以为点击没生效。
- ⇒ **结论：按住时长不是速率瓶颈**。1ms 已能触发吐孢 ⇒ 速率**完全由 `CLICK_MAX_PER_SEC` 闸门决定**（现为 **15/s**，相邻下发起点间隔地板 **67ms**），不再靠"按住多久"隐式限速。
  ⇒ 这也正是把按住压到 **1ms** 的理由：把"快慢"和"能不能点得动"两件事彻底解耦 —— 时长只管确定性，速率只管闸门；以后调速率不会碰到"按太短系统丢事件"的坑。
- ⇒ 子线程调 `press` **已验证可行**（上表第 3 行）：无需主线程配合。

- ⇒ **射程很短**：孢子基本**落在球的旁边**，**不是远程投射**（`TBD-18`）。所以吐孢是"就地投放"，摇杆方向只决定**往哪一侧放**。
- ⇒ **初速度很快**（口述 ≈5ms 就吐出来），但**射程极短**＋**只吐掉一点点质量** ⇒ 合起来 = **贴在球旁边的微量投放**。**不要**把吐孢当远程投送手段用；它只适合贴身微调（微降体积 / 就地推刺 / 向指定侧投放）。

### 6.5 飞出距离 ∝ 摇杆偏移量

```
flyDist ≈ SPLIT_FLY_K * |stickVector|      // |stickVector| ∈ [0,1] 归一化偏移量
```

- 摇杆拉到**最外** → 新碎片飞得**稍远**
- 手指在**摇杆中心附近** → 飞得**稍近**

⇒ 想**远射**吃球：先把摇杆拉满，再按分身；想**贴身**合体：摇杆居中，再按分身。

- **⚠️ 推论（待实测）**：摇杆居中 ⇒ 偏移量＝`0` ⇒ 方向取 `stickCenteredDir()`（单球→`lastMoveDir` / 多球→外接圆圆心）而**距离应为最小**（新碎片几乎贴着原球飞出）。⇒ **"居中按分身"＝朝居中方向、最小距离的分裂**。该推论未经实测（`TBD-14`）。

### 6.6 瞬间合球（回收碎片）

多球状态下，把各碎片**指向同一位置**使其迅速重叠 ≥30% ⇒ **立刻合并**（`00` M05，**无冷却**）。
⇒ 这是"分裂吃人之后把碎片收回"的主力动作；快循环应把它做成一个原子动作：**朝某点聚拢**。
⇒ 摇杆居中（6.2）是它的**被动版**（慢慢收），主动把摇杆指向一点是它的**加速版**。
