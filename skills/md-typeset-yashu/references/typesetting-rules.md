# Markdown 排版优化规则集

本文件是 `md-typeset` 技能的详细执行规则。排版执行时按本文件逐项处理。

## 1. 中文排版规范

### 1.1 中英文之间加空格

中文与英文、阿拉伯数字之间加一个半角空格。

| 原文 | 优化 |
|------|------|
| `这是一篇关于AI的文章` | `这是一篇关于 AI 的文章` |
| `2024年的第3季度` | `2024 年的第 3 季度` |
| `使用Python3.12版本` | `使用 Python 3.12 版本` |

**例外（不加空格）：**
- 英文缩写紧贴中文标点时，如 `AI，` 而非 `AI ，`（标点本身处理见 1.2）。
- 专有名词内部，如 `GitHub`、`iPhone`、`iOS`。
- 已是英文短语内部的空格保持原样。

### 1.2 标点全半角统一

**正文使用中文全角标点：** 逗号 `，`、句号 `。`、问号 `？`、感叹号 `！`、顿号 `、`、引号 `""`/`''`、书名号 `《》`、破折号 `——`、省略号 `……`。

**特殊情况：**
- 英文段落或代码注释中保持半角标点。
- 引用英文原文时保留原文标点。
- 括号：中文段落用全角 `（）`，含英文/代码内容时可用半角 `()` 以避免排版错位。
- 冒号：中文段落用全角 `：`。

### 1.3 数字处理

- 中文与阿拉伯数字之间加空格（见 1.1）。
- 纯数字单位组合不加空格：`3天` → `3 天`、`100元` → `100 元`（加空格）。
- 百分号：`50%` 保持紧贴（不加空格）。
- 日期：`2024年7月28日` 保持中文写法不加空格。

## 2. 标题层级规则

### 2.1 层级调整决策树

```
全文扫描标题层级 →
├── 有多个 H1（#）？
│   └── 是 → 文章主标题保留第一个为 H1，其余 H1 降为 H2（除非明显是独立章节标题）
├── 出现层级跳跃（如 H2 直接到 H4）？
│   └── 是 → 补齐层级或上调下层标题到相邻层级（H2 → H4 的情况：H4 上调为 H3）
├── 同级标题风格不一（有的带序号、有的不带）？
│   └── 是 → 统一风格：要么全部带序号，要么全部不带；按多数派统一
└── 标题文字有冗余空格 / 半角标点？
    └── 是 → 润色：去首尾空格、半角标点改全角、补全序号空格
```

### 2.2 标题润色允许的操作

| 操作 | 允许 | 示例 |
|------|------|------|
| 调整 `#` 数量 | ✅ | `## 标题` → `### 标题` |
| 去标题首尾空格 | ✅ | `##  标题 ` → `## 标题` |
| 半角标点改全角 | ✅ | `## 1.前言` → `## 1. 前言` |
| 补序号空格 | ✅ | `## 1.前言` → `## 1. 前言` |
| 统一序号风格 | ✅ | `## 一、前言` / `## 1. 前言` 统一 |
| **精炼标题文字** | ✅ | `## 关于我个人的一些感想和体会` → `## 个人体会`（删冗余，主题不变） |

### 2.3 标题留白

- H1 / H2 前**空两行**（视觉分隔大章节）。
- H3 及以下前**空一行**。
- 所有标题后**空一行**再接正文。
- 文档首行是标题时，标题前不空行。

### 2.4 标题文字精炼

排版时允许对标题文字进行适度精炼，使标题更简洁、更准确。边界如下：

**允许的操作：**
- 删除冗余修饰词（如「关于」「一些」「我个人」「浅谈」「试论」等不增加信息量的词）。
- 缩短啰嗦表述（如「如何有效地提升工作效率」→「如何提升工作效率」）。
- 使模糊标题更准确（如「那个东西」→「配置文件」，前提是正文内容确实讲的是配置文件）。
- 统一同级标题的句式结构（如有的用动宾、有的用名词短语，可统一风格）。

**禁止的操作：**
- 改变标题所指涉的主题（如「Python 入门」不可改为「Python 进阶」）。
- 添加原文标题和正文中都没有的新概念。
- 将标题改为与正文内容不匹配的表述。

**判定原则：**
1. 精炼后的标题必须仍能被正文内容支撑。
2. 拿不准时保留原文标题，不强行精炼。
3. 精炼幅度宜小不宜大——优先删词、缩句，慎用完全重写。

**示例：**

| 原标题 | 精炼后 | 说明 |
|--------|--------|------|
| `## 关于我学习编程的一些心得体会` | `## 学习编程的心得` | 删冗余修饰 |
| `## 怎么才能让团队里的每个人都愿意主动去沟通` | `## 如何让团队主动沟通` | 缩短啰嗦表述 |
| `## 其他` | `## 部署与运维` | 使模糊标题更准确（正文确实讲部署运维） |
| `## Python 入门指南` | `## Python 进阶技巧` | ❌ 改变了主题，禁止 |

## 3. 段落留白规则

### 3.1 量化标准

| 场景 | 空行数 |
|------|--------|
| 段落与段落之间 | 1 行 |
| 段落与列表 / 引用 / 代码块之间 | 1 行 |
| 列表 / 引用 / 代码块与后续段落之间 | 1 行 |
| 列表项之间 | 0 行（紧凑列表） |
| 连续多个空行 | 合并为 1 行 |
| 文档末尾 | 0 行多余空行 |

### 3.2 禁止的留白问题

- 标题紧贴正文（必须留白）。
- 段落内换行未用空行分隔（导致渲染为同段）。
- 连续 2 行以上空行（合并为 1 行）。
- 文末残留多个空行（删除）。

## 4. 列表规则

- **无序列表统一用 `-`**（不用 `*` 或 `+`）。
- **有序列表用 `1.` 起始**，让渲染器自动编号；不硬编码 `2.` `3.`（除非需要指定序号）。
- **嵌套缩进 2 空格**（Obsidian / 大多数 Markdown 渲染器兼容）。
- 列表项之间不空行（紧凑列表），除非列表项本身是多段内容（松散列表）。
- 列表前后各空一行与正文分隔。

## 5. 引用与 Callout 规则

### 5.1 普通引用 `>`

适用于：
- 引用他人原文、名言、文献。
- 纯叙述性的补充说明。

### 5.2 Callout 升级决策

当引用块内容性质属于以下之一时，**升级为对应 callout**：

| 内容性质 | Callout 语法 | 典型场景 |
|----------|--------------|----------|
| 一般提示 / 补充信息 | `> [!note]` | 背景说明、术语解释 |
| 实用技巧 / 建议 | `> [!tip]` | 操作建议、最佳实践 |
| 警告 / 注意事项 | `> [!warning]` | 风险提示、易错点 |
| 重要 / 必读 | `> [!important]` | 关键结论、必读事项 |
| 引用名言 / 金句 | `> [!quote]` | 名人名言、原文摘录 |
| 示例 / 案例 | `> [!example]` | 案例展示、代码示例 |
| 一般信息 | `> [!info]` | 元信息、注释 |
| 谨慎 / 风险 | `> [!caution]` | 高风险操作提示 |

**Callout 语法示例：**

```markdown
> [!tip]
> 这里是一个实用技巧：在 Obsidian 中按 Ctrl+E 可切换预览模式。
```

### 5.3 Callout 升级边界

- **纯叙述性引用（如引述他人一段话）保持普通 `>` 不动**，不强行加 callout 类型。
- 原文已有 callout 的，保留其类型，不改类型。
- 拿不准是否升级时，**默认保持普通 `>`**，并在交付说明中提示用户「可按需升级为 callout」。

## 6. 分割线规则

- 章节之间（H2 之间）插入 `---` 分割线，建立阅读节奏。
- 同一章节内的小节切换（H3 之间）**不**插入分割线（避免视觉过碎）。
- 话题明显转换但无标题处，可插入 `---`。
- 分割线前后各空一行。
- 短文（少于 3 个 H2）不强制加分割线。

## 7. 强调标记规则

### 7.1 高亮 `==text==`

- 用于强调文中本就关键的**单句或短语**。
- 每屏（约 5-8 段）不超过 1-2 处高亮。
- 不对整段高亮（视觉过载）。
- 不对普通陈述句高亮（只高亮结论性、定义性、警示性内容）。

### 7.2 加粗 `**text**`

- 保留原文已有的加粗。
- 不主动大面积添加加粗（适度型策略）。
- 标题不额外加粗（标题本身已突出）。

### 7.3 斜体 `*text*`

- 保留原文已有的斜体。
- 英文专有名词、书名等可考虑斜体，但不强制。

## 8. 代码块规则

- 代码块前后各空一行。
- 保留代码块的语言标识（```python 等）。
- **不改代码内容**，包括注释。
- 行内代码 `` `code` `` 前后无需空格调整（保持原样）。

## 9. 表格规则

- 表格前后各空一行。
- 可调整表格的对齐符号（`:`）使源码对齐美观，但**不改单元格文字**。
- 不主动新增表格（除非原文明显是表格数据但用了列表）。

## 10. 链接与图片规则

- 保留链接地址与链接文字。
- 保留图片地址与 alt 文字。
- 图片前后各空一行。
- 不主动给图片加尺寸标注（Obsidian 语法 `![[...]]` 原文已有则保留）。

## 11. 语气词清理规则

语气词清理是本技能允许的「文字级」操作之一（另一项是标题文字精炼，见第 2.4 节）。边界严格：仅删冗余口语填充词，不改写、不替换、不新增任何文字。

### 11.1 可删的语气词（句首 / 句中孤立口语填充词）

以下语气词在**句首或句中作为孤立填充词**出现时可删除：

| 语气词 | 典型可删场景 | 示例 |
|-------|-------------|------|
| 嗯 | 句首填充 | 嗯，我觉得… → 我觉得… |
| 啊 | 句首填充 | 啊，这件事… → 这件事… |
| 哦 | 句首填充 | 哦，原来如此。 → 原来如此。 |
| 哎 | 句首感叹 | 哎，真不容易。 → 真不容易。 |
| 唉 | 句首叹气 | 唉，没办法。 → 没办法。 |
| 嘛 | 句首填充 | 嘛，其实也行。 → 其实也行。 |
| 呃 | 句中填充 | 这个，呃，怎么说 → 这个，怎么说 |
| 那个 / 然后的话 / 就是说 | 口语串场填充 | 那个，我们开始 → 我们开始 |

删除时连同其后**多余的逗号**一并清理（如「嗯，」整体删除）。

### 11.2 不删的语气助词（句末承担语气功能）

以下助词位于**句末**，承担疑问 / 祈使 / 感叹等语气功能，**一律不删**：

| 助词 | 功能 | 示例（保留不动） |
|-----|------|------------------|
| 吧 | 祈使 / 推测 | 走吧。 / 应该吧。 |
| 呢 | 疑问 / 持续 | 怎么办呢？ / 还在呢。 |
| 吗 | 疑问 | 你知道吗？ |
| 呀 | 感叹 / 祈使 | 快来呀！ |
| 啦 | 感叹 | 好啦！ |
| 哟 | 感叹 | 注意哟。 |

### 11.3 判定原则

1. **位置优先**：句首 / 句中孤立、其后紧跟逗号停顿的，倾向可删。
2. **语义判断**：删掉后句子意思不变的才删；若语气词承担实质语气（如反问「不会吧？」），不删。
3. **句末保留**：位于句末标点（。？！）前的语气助词一律保留。
4. **重复冗余**：连续重复的语气词（如「嗯嗯」「啊啊」）合并或删除。
5. **拿不准保留**：无法确定是否冗余时，保留原文，不删。

### 11.4 示例

**原文：**
> 嗯，今天我们要聊的话题是关于效率的。啊，其实这个话题挺重要的。

**清理后：**
> 今天我们要聊的话题是关于效率的。其实这个话题挺重要的。

**原文：**
> 那个，我觉得吧，效率就是生命。

**清理后：**
> 我觉得吧，效率就是生命。（「那个」是句首口语填充，删；「吧」在句中保留语气）

## 12. 排版前后对照示例

### 示例 1：标题层级混乱

**原文：**
```markdown
# 我的一天
## 早上
### 起床
# 吃早饭
## 中午
```

**优化后：**
```markdown
# 我的一天

## 早上

### 起床

### 吃早饭

## 中午
```

### 示例 2：引用升级 callout

**原文：**
```markdown
> 注意：这个操作不可逆，请先备份数据。
```

**优化后：**
```markdown
> [!warning]
> 注意：这个操作不可逆，请先备份数据。
```

### 示例 3：中英文空格

**原文：**
```markdown
今天我用了Python写了一个API,效果不错。
```

**优化后：**
```markdown
今天我用了 Python 写了一个 API，效果不错。
```

### 示例 4：段落留白

**原文：**
```markdown
这是第一段。



这是第二段。
## 标题
紧贴标题的正文
```

**优化后：**
```markdown
这是第一段。

这是第二段。

## 标题

紧贴标题的正文
```

## 13. 执行检查清单

完成排版后，逐项自查：

- [ ] 全文最多一个 H1，无层级跳跃。
- [ ] 同级标题风格统一。
- [ ] 段落间空行统一为 1 行，无连续多空行。
- [ ] 标题前后留白符合 2.3 规则。
- [ ] 列表符号统一为 `-`，嵌套缩进 2 空格。
- [ ] 提示性引用已升级为 callout，叙述性引用保持 `>`。
- [ ] 章节间有分割线，章节内不过度切分。
- [ ] 中英文间有空格，标点全角统一。
- [ ] 高亮使用克制，每屏不超过 1-2 处。
- [ ] 正文内容基本保留，仅删除了冗余语气词（句首/句中填充），无其他文字改动。
- [ ] 标题精炼适度，未改变主题指向，精炼后仍被正文内容支撑。
- [ ] 句末语气助词（吧、呢、吗、呀等）未被误删。
- [ ] 代码块内容未动。
- [ ] 链接与图片未动。
- [ ] 文末无多余空行。
- [ ] 副本已生成，原文件未覆盖。
