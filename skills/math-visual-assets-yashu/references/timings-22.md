## 四、为什么"用了 GPU"还会超过 20 秒

这是本表最容易被误解的地方，单独解释。

### 4.1 GPU 只负责最后 0.1 秒

一次 860×860、2× 超采样（即 1720×1720 光线、300 步）的完整渲染，
在本机实测 **0.096 s**；单次 kernel 首次编译 **24 s**（冷启动），
开启落盘缓存后第二次起仅 **0.9 s**；EDT 改用 `edt` 包后从 9.6 s 降到 **0.30 s**。
**单张端到端：35.8 s → 2.6 s。**

也就是说 22 个图形里，**GPU 实际工作时间合计约 4 秒**
（其中曼德球一张就占 2.2 s，见 4.2 节末），
剩下的 273 秒全部花在 **CPU 上 numpy / scipy 搭建场数据**这一步。
换更快的显卡一分钱也省不下来，因为瓶颈根本不在 GPU。

### 4.2 超过 20 秒的 6 个图形，逐个归因

#### ① 阿波罗尼斯球夹 61.0 s（21.9%，最慢）

修好后采用"4 个正四面体相切球 + 中心隙球，反复球间反演 5 轮"，
生成 **6081 个球**。随后要让渲染器看到这 6081 个球的并集表面：

| 步骤 | 耗时 | 说明 |
|---|---|---|
| 反演生成 6081 球 | 1.7 s | 纯 Python 循环 |
| 体素占据标记 | 5.0 s | 6081 次 3D 子块距离计算 |
| **两次 `distance_transform_edt`（res=520）** | **47.5 s** | **主要瓶颈** |
| GPU 渲染 | ~2 s | 1720² × 300 步 |
| 合计 | 61.0 s | |

**为什么 EDT 这么慢**：scipy 的 EDT 是精确欧氏距离变换，
复杂度 O(N³)（N=520 → 1.4 亿体素），且**单线程、不走 GPU**。
必须跑两遍（一次求内距离、一次求外距离）才能夹出壳层。

> **可优化方向**：这对球并集其实有 O(N) 的精确解法 ——
> 对每个体素取"到最近球心的距离 − 该球半径"的最小值，
> 即 `min_i(|p − c_i| − r_i)`，可在 GPU 上一次 kernel 算完（6081 球 × 1.4 亿体素
> 在 4060 Ti 上约 1–2 s）。本次未实现，因为需要改写引擎的场接口。

#### ② f 原子轨道 26.2 s / ③ d 原子轨道 26.1 s

轨道等值面是**逐点解析计算**的，没有任何可复用的解析场：

- 占据网格 `res=384` → 5.65 亿体素，每个体素都要算一次 `Y₃₀(θ,φ)`（含
  **勒让德多项式关联函数** `P₃⁰(cosθ)`，本身就是多轮递推）
- 再 `sdf_from_occupancy(..., res=384, smooth=0.8)` → 又两次 EDT（384³ = 5.65 亿）

即"最贵的解析计算 × 最大的网格"叠加，所以稳定在 26 s。

> **已修过的坑**（见 `recipes-22.md` #20）：原实现占据网格只有 240，
> 比 SDF 网格（384）还粗，SDF 只是在三线性放大一个块状掩膜，提 SDF 的 res 完全无效。
> 两者必须同时提到 384 才有效 —— 这就是它现在要 26 s 的原因，是正确性的代价。

#### ④ 螺旋面 23.8 s / ⑤ 克莱因瓶 23.2 s

参数曲面 → 点云 → SDF 的路线，瓶颈同 EDT：

- 克莱因瓶：`param_cloud(1400×1400)` = **196 万个采样点**，
  再 `sdf_from_points(res=340)` → 340³ = 3900 万体素，EDT 约 20 s
- 螺旋面：参数域需要很密的采样才能覆盖 `r = aθ` 的长条，
  点数与网格都不小

> **共同规律**：曲面类耗时 ≈ `O(res³)`，由 EDT 主导。
> 想提速直接降 `res`（340→260 大约省一半），比减少采样点有效得多 ——
> 因为瓶颈是网格体积，不是点数。

#### ⑥ 克利福德吸引子 20.4 s / 洛伦兹 15.7 s / de Jong 16.1 s

这类不做 EDT，走**体积发光积分**：迭代点云 → `_tube_from_points` 建管
→ 沿视线积分。其中形态学膨胀（`close`）和 EDT 建管仍在 CPU 上：

- 克利福德：130000 点，`close=2` 需 6 次 6 邻域膨胀（每次遍历 420³ bool 数组），
  再两次 EDT
- de Jong：修复后 200 万点、`res=460` EDT

### 4.3 唯一的例外：曼德球 2.2 s 是**真的花在 GPU 上**

2026-10-06 曼德球改成解析距离估计场后，CPU 侧几乎不花时间（无网格、无 EDT），
**2.19 s 全部是 GPU 在跑光线步进** —— 因为它的场每求值一次就要迭代 16 次，
每次带 `acos / atan2 / sin / cos / pow`（`dr = r^(p−1)·p·dr + 1` 还能复用
`r^p/ r` 省掉一个 `pow`）。这是全部图里**唯一一张"GPU 是瓶颈"的图**。

对比参照：同样 860×860、ss=2、300 步的 gyroid（每次求值 3 个 `cos`）只要 **0.09 s**。
所以这里说"换显卡无效"要加一句限定：**除曼德球外**。

### 4.4 一句话总结

> **GPU 只承担"沿视线求交 + 着色"这一步（0.1 s 级）**；
> **其余 99% 的时间花在 CPU 上把隐式场/点云变成一张 3D 距离场网格**。
> 优化这个技能应该去优化 `scipy.ndimage.distance_transform_edt` 的调用次数与
> 网格分辨率，或者把建场搬到 GPU 上，**换显卡无效**。
> 唯一的例外是曼德球（4.3）：它没有 CPU 建场那一步，瓶颈真的在 GPU。

## 五、曼德球：2026-10-06 已修复（旧文档的结论是误诊）

**旧结论**：场数值正确、两条引擎都渲成管子、责任在表面渲染器 —— **错**。

**真正的根因**：场景把三维坐标塞进了**一个**复数。

```python
z = (X + 1j * Y).ravel() + 1j * Z.ravel()      # == X + i·(Y+Z)
```

一个复数只有实部虚部两格，这句直接把 `y` 和 `z` 挤进了同一个虚部。
于是整个场只依赖 `x` 与 `y+z` —— 场沿 `(0,1,−1)` 方向**恒定不变**，
它就是"二维集合沿该方向拉伸出的棱柱"，渲出来必然是那根光滑管子。
两种引擎结果相同，不是因为渲染器错，而是因为**它们读的是同一个错场**。

**复现证据**（任一时刻都能重跑）：

```python
a = field(X, np.zeros_like(X), Z)            # y = 0 切片
b = field(X, 0.4*np.ones_like(X), Z - 0.4)   # y = 0.4 且 z 平移 −0.4（保持 y+z）
np.array_equal(a, b)     # -> True，两个切片逐位相同
```

**修复方式**：换成解析距离估计场 `F_MANDELBULB`（球坐标幂映射），
不建网格、不跑 EDT。耗时从 3.4 s 降到 **2.19 s**，且不再有占据率量化误差。

**同时修掉的两个真实缺陷**（都只存在于 DE 写法里，与上面的根因无关）：

1. `de = r·log(max(r, 1.001))/|dz|` 用 `maximum` 截掉了 `log` 的负号 ——
   内部 `r<1` 的点本该是负值，被翻正后场的内部消失。
2. float64 下 `z**8` 溢出成 inf → NaN，NaN 与任何阈值比较都是 False，
   体素静默退出占据场，在物体上打出隧道（res=80 时 19% 的格子是 NaN）。

**验证**：240×240 同图对照，CPU vs GPU **IoU = 0.991**、maxdiff 0.079。

> 💡 **方法论教训**：当两条独立引擎给出**相同的错误结果**时，先假设
> "它们读的是同一份错误输入"，而不是"两个渲染器都错了"。
> 后者在概率上几乎不可能；前者只要一句 `array_equal` 就能证死。
