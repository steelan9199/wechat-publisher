# 规则生命周期示例

## 示例 1：重复规则合并

- 原始规则 A：输出前检查标题是否过长。
- 原始规则 B：标题不要超过 20 个汉字。
- 原始规则 C：如果标题太长，改成更短的标题。

处理：

1. 合并为一条规则：`当生成标题时，检查标题是否超过约定字数；超出则压缩并保留核心信息。`
2. 字数阈值放入对应 checklist。
3. 记录 A/B/C 的原位置和合并后的规则 ID。

错误做法：直接删除 A 和 C，且不保留来源映射。

## 示例 2：抽象原则改写

- 原始规则：回复要专业但不要生硬。

推荐处理：

- 保留为语气原则。
- 补充触发场景：当向客户提出时限、补材料或纠正错误时。
- 提供反例、正例和边界例。
- 将最终语气检查放入交付验收单。

错误做法：因为写不出精确条件就立即删除。

## 示例 3：规则退休

- 原始规则：导出 CSV 时必须使用 GBK 编码。
- 新证据：当前客户系统和内部规范均要求 UTF-8，GBK 曾导致乱码事故。

处理：

1. 将 GBK 规则标记为退休。
2. 新规则写明 UTF-8 及例外审批条件。
3. 将旧规则保留在历史说明或事故案例中。
4. 增加 UTF-8/GBK 的回放测试。

错误做法：无证据地用个人偏好替换编码规则。

## 示例 4：规则自动化

- 原始规则：所有 Markdown 链接必须有效。

推荐处理：

- 保留人工验收项，同时增加链接检查脚本或命令。
- 将失败输出作为交付前阻断条件。
- 对无法自动判断的链接保留人工复核。

收益：机械判断不再依赖模型记忆。
