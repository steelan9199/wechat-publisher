# 信息架构与渐进披露

## 什么时候读我

当需要决定规则放在哪里、是否拆分文件、如何挂指针、如何降低常驻上下文或设计示例/验收单时，读本文件。

## 1. 加载层级

| 层级 | 内容 | 加载时机 |
|---|---|---|
| 元信息 | name、description | 常驻，用于技能路由 |
| 主入口 | SKILL.md 的定位、硬门禁、主流程、索引 | 技能相关时加载 |
| 按需资料 | references、examples、checklists、assets | 触发具体场景时读取或使用 |
| 可执行能力 | scripts、校验器、自动化工具 | 需要时执行，不一定读入上下文 |
| 评测资产 | evals、测试任务、历史事故 | 改造前后验证使用 |

## 2. 规则放置决策

| 规则特征 | 推荐位置 |
|---|---|
| 高频、关键、违反即失败 | 内联到主流程对应步骤 |
| 低频但风险高 | 主流程挂直达指针，正文放 reference |
| 内容庞杂、只在特定场景需要 | 独立 reference，并写明“什么时候读我” |
| 交付后可逐项判断 | checklist |
| 依赖主观判断或容易漂移 | 正反例 + 边界例 |
| 可机械判断 | 脚本、schema、lint、测试或校验器 |
| 已失效且无保留价值 | 规则退休；必要时转为历史案例 |
| 解释背景和原理 | 独立说明，不阻塞执行步骤 |

## 3. 拆分与打包

- 按“用户/Agent 做哪个动作时需要它”打包，而不是按作者的学科分类。
- 高频高风险内容靠近触发动作；低频内容通过指针访问。
- 文件开头提供一句话适用场景；较长文件提供目录。
- 同一 reference 应围绕同一任务目标，避免重新变成大而全手册。
- 避免过度拆分：如果多个规则总是同时触发，应保留在同一文件中。
- 文件名表达用途和触发时机，避免“最终版”“规范 2”“工具 1”等名称。

## 4. 索引要求

主入口应保证：

- 每个按需文件都有明确入口。
- 每个高风险动作都能沿主流程找到对应规则。
- 每个留存脚本都说明何时调用、输入输出和依赖。
- 每个 checklist 都被流程中的交付/验收步骤引用。
- 每个示例都与具体规则或失败模式相连。

## 5. 常见反模式

- 关键规则只写在分类章节深处。
- 文件拆出后主流程没有指针。
- 主入口同时承载大量场景细则、示例和格式偏好。
- 为了“以防万一”保留无触发条件的规则。
- 只做人工走查，不做任务回放和自动化验证。
- 把所有 checklist 都当成格式偏好，忽略安全、功能和合规验收。

## 6. 依据边界

渐进披露、信息架构和长上下文位置效应有外部实践与研究支持，但具体文件数、行数和评分阈值属于工程启发法，应按目标 Skill 的运行时和风险等级校准。
