# 代码与脚本治理

## 什么时候读我

当目标 Skill 包含 scripts、文档内嵌可执行代码、命令行工具、自动化校验器，或改造可能影响代码行为时，读本文件。

## 1. 最高原则

文档信息架构治理默认 **不改变代码可观察行为**。若需要修复 Bug、新增功能、改变参数或调整算法，必须从文档治理中拆出，作为独立变更审批。

## 2. 允许与禁止

| 动作 | 文档治理阶段是否允许 |
|---|---|
| 移动脚本、重命名文件、归置目录 | 允许，但需同步引用并验证 |
| 修改因移动产生的 import/路径 | 允许，原则上只改路径字符串 |
| 补充文件头注、使用说明、非显然注释 | 允许，不改变逻辑 |
| 在文档中挂脚本指针 | 允许 |
| 修改函数逻辑、参数、返回值、算法 | 不允许，需独立变更 |
| 修改依赖版本、安装命令、环境配置 | 不允许，需评估并审批 |
| 拆分巨型脚本、抽象函数、改异常处理 | 不允许，需测试和审批 |
| 修复 Bug 或新增功能 | 不允许混入，需独立任务 |

## 3. 改造前安全网

移动或重构代码前，按可得性依次建立：

1. 自动化单元测试和集成测试。
2. 命令行快照或输入输出 golden files。
3. 特征测试：先记录现有行为，即使行为看起来不完美。
4. 静态检查、lint、类型检查或语法检查。
5. 依赖版本和运行环境记录。
6. 整目录备份与哈希清单。

没有测试时，不应进行较大代码重构；用户明确要求冒险时，也要缩小改动范围并记录限制。

## 4. 行为保持型重构

重构应小步进行：

1. 确认当前测试通过或记录基线。
2. 执行一个极小的结构调整。
3. 运行相关测试/快照。
4. 失败则立即还原或修正。
5. 重复直到目标结构达成。

重构与新增功能应分开；同一轮中同时“重构 + 改行为”会降低可追溯性。

## 5. 脚本组织

每个留存脚本应在头部或文档中说明：

- 做什么
- 什么时候使用
- 由哪个流程步骤调用
- 输入参数和输出产物
- 依赖与运行方式
- 常见失败和安全限制

孤儿脚本不得擅自删除；先标记为待确认，由用户决定保留、归档、转为示例或退休。

## 6. 验证最低要求

- 语法/类型检查通过。
- 关键命令可运行。
- 移动后的路径和调用点有效。
- 典型输入输出与基线一致。
- 高风险脚本有权限、网络和写入范围说明。
- 变更清单逐项列出代码文件和原因。
