# 操作流程：五步治理法（踩坑文章的落地版）

适用于阶段一规则梳理与阶段二搬家的总操作顺序。找整块时间，把规则库摊开，五步走完。

## 第一步：摊开重标（只贴标签，不删不改）

给每条规则打三个标签：
- 后果：致命 / 可补救 / 只是丑
- 场景：全局 / 具体场景（写清是哪个动作）
- 时机：执行前必须知道 / 输出后核对即可

产出规则标签总表。贴完即能第一次看清规则库的真实构成。

## 第二步：抓冲突，不抓重要性

永远不问「哪条更重要」（血泪史面前答案永远是「都重要」），只问两个答得上来的问题：
1. 「这两条打架时听谁的？」——找出矛盾规则（如「尽量简短」vs「每个问题解释清楚」），当场写定仲裁原则并写入文档。
2. 「违反这条，会死人吗？」——给后果定级。

顺手合并重复：同一个坑换三种说法写了三遍的，合并为最全的一条表述；体量往往先砍掉一半。合并是去重，不是删除知识。

## 第三步：分层归位

- 致命 + 全局 → L0，控制个位数；
- 具体场景 → 改写为「当 X 时……」条件块，拆独立文件，主文件挂索引指针；
- 格式偏好 → 后移编验收单；
- 能举对照例子的 → 改判例。

## 第四步：给宪法装熔断条款

逐条检查 L0：每条红线后面有没有「立即停止 + 找人确认」的显式动作？没有就补。红线没有熔断条款 = 没写。

## 第五步：翻车回放，逐个验收

- 列出过去真实踩过的坑（它们是规则存在的原因），逐个走查：新架构下坑再现时，对应规则会不会在该触发的位置被准时读到？
  - 红线类：是否每次都在场？
  - 场景类：L1 有无索引指针？
  - 格式类：验收单上有无该项？
- 读不到 = 架构没到位，继续搬位置。
- 验收标准是「坑还会不会再踩」，不是「规则还在不在文档里」。

## 两种上架手法的选择

- 高频致命 → 内联进 L1 步骤；
- 庞杂低频 → 挂索引指针。
- 既无内联也无指针 = 等死架构，必改。
