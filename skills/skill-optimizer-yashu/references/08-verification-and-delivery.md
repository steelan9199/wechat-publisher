# 验证、交付与监控

## 什么时候读我

当改造完成、需要宣布完成、交付变更说明或建立后续监控时，读本文件。

## 1. 验证层级

| 层级 | 检查内容 |
|---|---|
| 文件系统 | 文件存在、路径正确、目录无意外变更、备份完整 |
| 链接引用 | Markdown 链接、相对路径、脚本引用、旧名悬挂引用 |
| 元信息 | name、description、触发范围、长度和语义清晰度 |
| 路由能力 | 触发、改写触发、非触发、冲突 Skill 用例 |
| 任务能力 | 典型任务、完整交付、输出格式、验收标准 |
| 代码脚本 | 语法、类型、单元/集成测试、命令执行、输入输出 |
| 风险合规 | 安全、隐私、法律、权限、外部写入和数据处理 |
| 历史事故 | 事故回放、失败注入、边界条件和回归结果 |
| 确定性结构校验 | frontmatter、Markdown 相对路径、孤儿文件、YAML、临时/备份文件 |

可运行下面的命令输出可复核的结构校验结果（**用 py314-cpu 环境解释器**，系统 `python` 缺 PyYAML 会报假故障）：

```powershell
& "D:\software\uv\envs\py314-cpu\Scripts\python_direct.exe" scripts/validate_skill.py <skill-root> --json
```

校验器会先剔除代码围栏（``` 与 ~~~）再解析行内路径。报“孤儿”时先确认该路径是不是只出现在代码块里；报“无效引用”时确认路径是否本来就相对于运行目录（而非技能根目录）的资产。

符号链接：技能根目录是链接时校验器照常工作，并在 `warnings` 里给出真实内容路径；技能内部的目录链接会被跟随（含环检测），被跟随的链接列在 `symlinked_dirs_followed`，所以报出的 `file_count` 覆盖链接内容，不再静默漏检。注意：不跟随链接的盘点工具（bash `find` 的默认行为）会给出偏少的文件数，不能据此下结论。

### 豁免清单

校验器不会对所有文件一视同仁。以下对象被**主动排除**，不参与引用检查和孤儿判定；报出的数字不含它们，排查时不要把它们当成漏检：

| 豁免对象 | 判定方式 | 理由 |
|---|---|---|
| `__pycache__/`、`*.pyc`、`*.pyo` | 目录名/后缀 | 运行时生成物，非作者编写的技能内容 |
| `.git/` | 目录名 | 版本控制元数据，读者无法从入口到达 |
| `node_modules/`、`vendor/`、`third_party/` | 目录名 | 第三方依赖，其 README 与清单描述的是**别的项目**的布局 |
| `.venv/`、`venv/`、`.cache/`、`dist-info/`、`egg-info/` 等构建缓存 | 目录名 | 同上，非技能内容 |
| 工具脚本 | **角色**判定：位于 `scripts/`、`tools/`、`bin/` 下，扩展名属脚本类，且文件名含 `validate`/`check`/`lint`/`verify`/`audit`/`inspect`/`format` 之一 | 工具脚本由流程**调用**而非从正文**指向**，"无入口指针"是预期行为，不是孤儿 |

工具脚本的豁免按**角色**而非固定文件名给定。早前版本硬编码 `scripts/validate_skill.py` 一个路径，脚本一旦改名（如 `validate-skill.py`）就立刻把自己报成孤儿，也无法覆盖第二个校验器；改为角色判定后这两种情况都正确。

同时，以下形态**不算引用承诺**，因此不会报死链——它们是文档在演示"该怎么写"，而不是技能应当携带的文件：

- 链接语法占位符：`[文本](url)`、`[label](link)`
- API 占位 id：`![Image](img_xxx)`、`file_xxx`、`res_123`
- 单字母示例名：`./a.png`、`a.png`
- 中文占位名：`图片文件名.png`、`示例文件名.md`
- 代码围栏内的任何路径（围栏先被剔除）
- URL（含出现在行内代码中的 URL）与整条命令行

`如果某次报出的"无效引用"看起来像上面这一类，先确认它是否真的落在豁免范围内；确属误报请按 `evals/optimizer-regression-cases.md` 补一个夹具用例再改代码。`

## 2. 前后对比

至少报告：

- 触发召回率/精确率或用例通过数。
- 任务成功率和关键错误变化。
- 沉底规则、孤儿文件、死规则、死链数量。
- 主入口和强制读取内容的行数/token 变化。
- 新增、移动、合并、改写、暂停、退休、删除的文件。
- 未完成项、残余风险和需要用户决策的事项。

## 3. 交付内容

1. 新版 Skill 路径。
2. 备份路径和哈希清单。
3. 《诊断报告 + 改造蓝图》批准记录。
4. 变更清单：新增、移动、重命名、合并、修改、退休、删除。
5. 规则映射：原规则到新规则/新位置/退休状态。
6. 验证结果：测试、检查、回放、失败注入和验收单。
7. 指标前后对比。
8. 残余风险、缺口、后续监控和复测建议。

## 4. 完成判定

只有同时满足以下条件，才可宣布完成：

- 用户批准的蓝图动作均已执行或明确说明未执行原因。
- 备份和回滚路径可用。
- 所有留存文件可从入口追踪到用途。
- 关键任务和历史事故回放通过。
- 高风险代码和外部写入路径已验证。
- 验收单中失败项已修复或被用户接受。
- 最终交付不把搜索结果、假设或未验证判断写成事实。

## 5. 后续监控

建议跟踪：真实任务触发情况、误触发/漏触发、用户返工、脚本失败、失效链接、规则冲突、事故复发和评测样本变化。新的失败案例应补充到 `evals/`，形成持续回归。
