# 治理规范：代码与脚本资产（scripts / 工具脚本 / 文档内嵌代码）

## 最高约束：逻辑零改动

- 允许：文件移动与目录归位、文件重命名（按命名规范）、新增或补全文件头注、为非显然逻辑补说明性注释、在文档中挂使用指针、同步修正因移动导致的调用路径。
- 禁止：改动函数逻辑、增删功能、修改参数与返回值、调整算法、变更依赖清单与版本号。
- 因文件移动必须修改 import / 路径时：只改路径字符串，不改其他任何代码，并在变更清单中逐项列出。
- 拿不准某处改动是否属于「逻辑改动」→ 一律视为逻辑改动，保留原状，在蓝图中标注请用户决定。

## 组织治理

1. 脚本统一归置 scripts/（或目标 skill 既有约定目录），按「动作 / 场景」分子目录，不按编写时间堆放。
2. 消灭孤儿脚本：每个脚本都必须被 SKILL.md 或某份文档的指针引用；无引用脚本标记为「疑似孤儿」进入蓝图，由用户确认去留，禁止擅自删除。
3. 一个脚本对应一类明确任务；职责混杂的巨型脚本只在报告中建议拆分，不代为拆分（拆分属逻辑改动）。

## 注释与头注规范

每个脚本文件头部补充（缺失才补，已有则保留）：
- 这个脚本做什么（一句话）
- 什么时候用 / 由哪个流程步骤调用
- 输入与输出（参数、产物）
- 依赖与运行方式（原文已有则引用，不编造命令）

函数级注释只补「为什么这么做」的非显然逻辑；显而易见的代码不加噪注释。

## 文档-代码指针挂接

- SKILL.md 的 L1 步骤中，凡需调用脚本处写明：「执行 `scripts/xxx.py`（用途见文件头注）」。
- 脚本头注反向写明调用它的流程步骤，形成双向可追溯。
- Markdown 中内嵌的代码：短片段保留原位；成段可执行脚本应抽成独立脚本文件并挂指针（涉及代码搬运，须在蓝图中列明并经确认）。

## 审计要点

- [ ] 孤儿脚本数 = 0（或全部已标注待用户确认）
- [ ] 每个脚本有头注，且含「什么时候用」
- [ ] L1 中每个脚本调用点都有指针
- [ ] 脚本按动作归目录，命名达意
- [ ] 逻辑零改动（移动后路径修正除外），已逐文件比对
