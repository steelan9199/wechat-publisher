# Skill Laws（设计法则）

> **核心理念**：Skill 是给 AI 用的，Skill的完整名字是`Agent Skill`, 一个Skill通常只包含一个功能，或者一件事情的SOP（操作步骤）。Skill中包含的是各行各业的【人类或者AI】做事情或者解决问题的经验，把经验沉淀到skill中，这样别的AI读到这个skill之后，就可以按照它里边的操作步骤来完成任务。

---

## 功能概述

本 Skill 是 Skill 设计的通用法则框架，用于规范所有 Skill 的创建、优化与评估流程。它提供可操作的执行步骤、统一检查表与报告模板，确保 Skill 文档对 AI 友好、对人类可读。

## 环境说明

- 本 Skill 为通用框架，适用于任何类型 Skill 的创建、优化与评估，不绑定特定技术栈或目录结构。
- 执行时以目标 Skill 的`SKILL.md` 为核心操作对象，工具调用以目标 Skill 所在路径为上下文。
- 下文出现的 `{skill-name}`、`{skill-path}` 等变量，均需根据实际目标 Skill 替换为真实值。
- 不同软件的 Skill 存放目录不同（如 `.skills/`、`.trae/skills/` 等），创建时以当前环境的实际路径为准。

### $SKILL_DIR（Skill 目录变量）

`$SKILL_DIR` 指当前 Skill 所在的绝对目录，即 `SKILL.md` 文件所在的文件夹。若 Skill 包含脚本/代码，必须在【环境说明】中定义此变量和脚本执行路径。详见 [references/skill-dir-guide.md](references/skill-dir-guide.md)。

> **路径前缀强制规则**：Skill 文档中所有引用 Skill 内部文件（脚本、配置、references 文档等）的路径，**必须以 `$SKILL_DIR` 为前缀**写明绝对路径或基于 `$SKILL_DIR` 的相对路径。AI 加载 Skill 后可直接定位文件，无需搜索。禁止只写相对路径（如 `references/guide.md` 或 `./scripts/build.js`），应写为 `$SKILL_DIR/references/guide.md` 和 `$SKILL_DIR/scripts/build.js`。

## 渐进披露设计指南

Skill 文档必须分层设计，AI 先读共性（SKILL.md），按需加载个性（references/）。分层不清会导致 SKILL.md 臃肿，AI 上下文浪费。

### 三层结构

| 层级      | 文件                          | 作用                     | AI 加载时机          |
| --------- | ----------------------------- | ------------------------ | -------------------- |
| L1 共性层 | `SKILL.md`                    | 所有功能都依赖的公共信息 | 每次必加载           |
| L2 索引层 | `references/{功能}-api.md`    | 某一类功能的流程索引     | 匹配到对应功能时加载 |
| L3 细节层 | `references/{功能}/{细节}.md` | 单个脚本/接口的详细说明  | 需要调试或深入时加载 |

### 共性内容（必须留在 SKILL.md）

删除以下内容会导致**所有功能**无法正常执行，因此必须留在主文件：

1. **触发与意图**：description、自然语言调用规则、触发关键词
2. **功能概述**：一句话说明 Skill 是做什么的
3. **环境说明**：`$SKILL_DIR`、Shell 类型、脚本目录、依赖安装方式
4. **全局前置条件**：所有功能都需要的前提（如 API Key、全局配置文件的读取路径）
5. **全脚本索引清单**：所有可用脚本的列表（仅名称+一句话功能，不含详细参数）
6. **跨功能公共规则**：所有脚本都必须遵守的调用规范（如"执行前必须 cd 到 scripts 目录"）
7. **公共能力与全局错误**：多个子功能共用的能力（如上传文件）、所有功能都可能遇到的错误

### 个性内容（必须下沉到 $SKILL_DIR/references/）

以下内容只服务于**单一功能**，其他功能不需要它，必须下沉：

1. **单一功能的完整调用流程**：如"Bot 四步调用流程"、"Workflow 三步调用流程"
2. **单一脚本的详细参数说明**：参数类型、必填项、JSON 格式、校验规则
3. **单一功能的输入输出示例**：完整的命令行示例、返回数据示例
4. **专属错误**：只在该功能下才会出现的错误及处理方式
5. **子功能内部分支决策**：如"如果参数是文件类型，则用 file_id 方式传参"

### 判断口诀（共性与个性）

> 删除该段内容后，其他功能是否仍能正常执行？
>
> - **能** → 它是个性，下沉到 `$SKILL_DIR/references/`
> - **不能** → 它是共性，留在 `SKILL.md`

### 正反对照

| 场景     | ❌ 错误（留在主文件）                                        | ✅ 正确（下沉到 $SKILL_DIR/references/）                             |
| -------- | ------------------------------------------------------------ | -------------------------------------------------------------------- |
| Bot 调用 | SKILL.md 中写"步骤1：create_session，步骤2：send_message..." | SKILL.md 只写"参考 `$SKILL_DIR/references/bot-api.md`"，流程详情下放 |
| 参数说明 | SKILL.md 中解释 send_message.js 的 JSON 参数文件格式         | 在 `$SKILL_DIR/references/bot/sendMessage.md` 中解释                 |
| 环境说明 | 在 Bot 文档中重复说明"必须先 cd 到 scripts 目录"             | 只在 SKILL.md 中说一次，Bot/Workflow 文档直接引用                    |

| 20  | 脚本规范        | ES Module 强制   | 若 Skill 包含 `scripts/` 目录下的 `.js` 脚本文件，**必须使用 ES Module**（`import`/`export` 语法），禁止使用 CommonJS（`require`/`module.exports`）。同时 `scripts/package.json` 必须设置 `"type": "module"`，否则 Node.js 会将 `.js` 文件按 CommonJS 解析，导致语法错误。                                                                                                                                                                                                                                                                                                                                         |
| 21  | ⭐⭐⭐ 脚本规范 | 脚本文档强制读取 | 若 Skill 包含 `scripts/` 目录下的脚本，**在执行任何脚本之前，必须先读取对应的参考文档**（如 `$SKILL_DIR/references/bot/sendMessage.md`、`$SKILL_DIR/references/workflow/runWorkflow.md` 等）。这是避免参数格式错误的关键步骤。禁止凭记忆或直觉编写参数，必须严格按照文档中的格式要求操作。                                                                                                                                                                                                                                                                                                                         |
| 22  | 脚本规范        | 多行文本换行符   | **适用范围**：仅限 Skill 包含 `scripts/` 目录且其中有 Node.js `.js` 脚本。<br>**要求**：脚本中 `throw new Error(...)` 和 `console.error/log/warn(...)` 调用里的多行文本字符串，**禁止使用 `\n` 字面量**，必须使用 `os.EOL` 动态换行符。<br>**替换步骤**：<br>① 在文件顶部添加 `import { EOL } from "node:os";`（如已存在则跳过）<br>② 若原字符串为普通引号 `"..."`，先改为模板字符串 `` `...` ``<br>③ 将字符串中的 `\n` 替换为 `${EOL}`<br>**禁止替换的场景（豁免）**：<br>• `.join("\n")` 等数据拼接操作<br>• 正则表达式中的 `\n`<br>• Buffer/二进制操作中的 `\n`<br>• HTTP 协议头/消息体中的 `\r\n` 等协议级换行 |

## 创建模式

**触发**：用户要创建新 Skill

### 执行步骤

| 步骤 | 执行动作          | 具体命令/操作                                                                                                                                                        |
| ---- | ----------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 1    | 确定 skill 目录名 | 使用格式 `skill-{功能名}`，全小写，连字符分隔                                                                                                                        |
| 2    | 创建目录结构      | 运行 `mkdir` 创建 `{skill-path}/{skill-name}/{references,scripts}`                                                                                                   |
| 3    | 创建 SKILL.md     | 运行 `Write` 工具创建文件，路径：`{skill-path}/{skill-name}/SKILL.md`                                                                                                |
| 4    | 写入 frontmatter  | 复制下方模板，替换变量：`{skill-name}` `{功能描述}` `{触发条件}`                                                                                                     |
| 5    | 添加功能概述      | 在正文开头添加【功能概述】段落，说明 Skill 的核心功能与适用范围                                                                                                      |
| 6    | 添加环境说明      | 若 Skill 包含脚本/代码，定义 `$SKILL_DIR` 和脚本执行路径；若 Skill 无代码，描述运行上下文即可                                                                        |
| 7    | 添加执行步骤      | 若 Skill 包含多个功能（不同触发词对应不同执行流程），每个功能需要独立的执行步骤表格                                                                                  |
| 8    | 添加输出格式      | 明确说明每步执行后输出什么、最终输出什么格式                                                                                                                         |
| 9    | 检查统一检查表    | 对照【统一检查表】逐项验证，全部通过才算完成                                                                                                                         |
| 10   | 创建 references   | 对照【渐进披露设计指南】，将个性内容按功能拆分为独立文件：`$SKILL_DIR/references/{功能}-api.md`（L2 索引层）和 `$SKILL_DIR/references/{功能}/{细节}.md`（L3 细节层） |

### Frontmatter 模板

```yaml
---
name: {skill-name}
description: {功能描述}。何时使用：当用户{说/需要/遇到}{触发条件}时。
metadata:
  author: "{作者名}"
  updated: "{YYYY-MM-DD HH:MM:SS}"
  version: "1.0.0"
---
```

### 错误处理

| 错误场景   | 错误表现                            | 处理方式                                                         |
| ---------- | ----------------------------------- | ---------------------------------------------------------------- |
| 目录已存在 | `mkdir` 报错目录已存在              | 运行 `LS` 检查目录内容，如为空则继续，如有内容则询问用户是否覆盖 |
| 变量未替换 | SKILL.md 含 `{skill-name}` 等占位符 | 运行 `SearchReplace` 替换所有占位符为实际值                      |

## 优化模式

**触发**：用户要优化现有 Skill 或指出 Skill 有问题

### 执行步骤

| 步骤 | 执行动作       | 具体命令                                                   |
| ---- | -------------- | ---------------------------------------------------------- |
| 1    | 读取目标 Skill | 运行 `Read` 工具读取 `{skill-path}/SKILL.md`               |
| 2    | 逐项检查       | 对照【统一检查表】逐项标记 ✅/❌                           |
| 3    | 统计问题       | 统计 ❌ 项数量，按优先级排序（核心法则优先）               |
| 4    | 执行修复       | 运行 `SearchReplace` 或 `Write` 修复问题，参考【修复操作】 |
| 5    | 验证修复       | 重新对照【统一检查表】检查，确认修复未引入新问题           |
| 6    | 输出报告       | 按【优化报告模板】输出结果                                 |

### 正反对照（快速修复参考）

| ❌ 错误示例          | ✅ 正确示例                     |
| -------------------- | ------------------------------- |
| "你可以运行..."      | "运行..."                       |
| "建议检查..."        | "检查..."                       |
| "如果需要可以..."    | 改为条件表格："如果 X 则执行 Y" |
| "请参考文档了解详情" | "参考 [文件名](路径) 执行..."   |
| "确保 xxx"           | "运行 `命令` 检查 xxx"          |
| 长段落描述           | 表格/列表 + 具体命令            |

### 错误处理

| 错误场景         | 错误表现               | 处理方式                               |
| ---------------- | ---------------------- | -------------------------------------- |
| 无问题可优化     | 所有检查项都是 ✅      | 按【评估模式】输出评估报告             |
| 修复后引入新问题 | 修复 A 问题导致 B 问题 | 回滚更改，分步修复，每步修复后重新检查 |
| 用户不认可修复   | 用户说"不要改这个"     | 记录用户反馈，跳过该项，继续优化其他项 |

### 优化报告模板

```
## 优化报告：{skill-name}

**评分**：{通过数}/18 项符合（核心法则 2 项 + 文档规范 9 项 + 脚本规范 6 项 + 路径规范 1 项）

### 主要问题

1. {问题描述}
   - 修复操作：{具体操作}
   - 使用工具：{Read/SearchReplace/Write}

2. {问题描述}
   - 修复操作：{具体操作}
   - 使用工具：{Read/SearchReplace/Write}

### 已修复

- {修复内容}

### 后续建议

- {建议内容}
```

## 评估模式

**触发**：用户问 skill 设计得怎么样或要求评估 Skill 质量

### 执行步骤

| 步骤 | 执行动作       | 具体命令                                     |
| ---- | -------------- | -------------------------------------------- |
| 1    | 读取目标 Skill | 运行 `Read` 工具读取 `{skill-path}/SKILL.md` |
| 2    | 核心法则评估   | 检查是否符合【统一检查表】第 1-2 项          |
| 3    | 文档规范评估   | 检查是否符合【统一检查表】第 3-11 项         |
| 4    | 计算评分       | 统计符合项数，确定等级                       |
| 5    | 输出评估报告   | 按【评估报告模板】输出结果                   |

### 评估标准

| 等级      | 分数     | 说明                            |
| --------- | -------- | ------------------------------- |
| 🏆 完美   | 18/18    | 完全符合 Skill Laws，可直接使用 |
| ✅ 优秀   | 15-17/18 | 基本符合，少量细节可优化        |
| ⚠️ 良好   | 12-14/18 | 有明显改进空间                  |
| ❌ 需优化 | < 12/18  | 需要大幅重构                    |

### 错误处理

| 错误场景      | 错误表现                         | 处理方式                                                  |
| ------------- | -------------------------------- | --------------------------------------------------------- |
| 非 Skill 文件 | 文件不含 SKILL.md 结构           | 输出"该文件不是 Skill，无法评估"，说明 Skill 文件结构要求 |
| 评分边界      | 得分恰好在边界（如 5 分或 8 分） | 向下取整，按较低等级评定，鼓励继续优化                    |

### 评估报告模板

```
## Skill 质量评估：{skill-name}

### 总体评分

**符合度**：{X}/18 项 ✅

**等级**：{🏆/✅/⚠️/❌}

### 核心问题（如等级不为 🏆）

- {问题描述} → {改进建议}

### 建议操作

- ❌ 需优化：按【优化模式】执行全面优化
- ⚠️ 良好：针对核心问题逐一修复
- ✅ 优秀：微调细节即可达到 🏆 完美
```

## 通用错误处理

> 以下错误在所有模式中均可能发生，统一在此处理。

| 错误场景      | 错误表现                             | 处理方式                                                                                                                                                                                              |
| ------------- | ------------------------------------ | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 文件不存在    | `Read` 报错文件不存在                | 检查路径是否正确，如 skill-name 拼写错误，询问用户                                                                                                                                                    |
| 写入失败      | `Write` 返回错误                     | 检查路径是否正确，如路径含空格需用引号包裹，重试写入                                                                                                                                                  |
| Glob 参数错误 | `Glob` 返回"missing field `pattern`" | `Glob` 工具的 `path` 和 `pattern` 是两个独立参数，不要将完整路径当作 `path` 值，正确用法：`{"path": "目标目录", "pattern": "相对于path的glob模式"}`，例如 `{"path": "d:/project", "pattern": "*.js"}` |
